# gaudit — settled decisions

gaudit is a GNOME app that checks the security state of a computer for an ordinary user without special technical skills. The app **does not** take action itself (updating, virus scanning, etc.). It checks that things are in place and run regularly, and starts existing tools only when needed to get a status report.

**Scope:** gAudit secures the machine at an overall level. It checks that the basics are in place and working, and leaves specialised work to specialised tools (e.g. scanning single directories with ClamTk or ClamUI). When a check starts to need deep knowledge of one tool, the rest belongs in that tool.

This file collects decisions that have been made. Do not reopen them without a concrete reason. Write new decisions here.

## Goals and platform

- Language: C/C++.
- The GUI (controller and view) is written in C with GTK4/libadwaita. gtkmm was rejected: in other projects it lacked parts we needed.
- The model may be written in C++ where it pays off. The boundary to the C part is a plain C API:
  - `extern "C"` and opaque handles; no C++ types in headers the C code sees
  - no exceptions across the boundary, only status codes. Header declarations are marked `GAUDIT_NOEXCEPT` (`noexcept` in C++, empty in C) so the compiler enforces it.
  - clear memory ownership (whoever allocates, frees)
- The helper and the check processes are written in C. **Collectors that must use a C++-only library may be written in C++** (e.g. the dnf collector with libdnf5). They are separate processes, so no C++ types cross any boundary, only S-expressions over a pipe.
- First platform is the Debian family (Ubuntu, Debian and derivatives). Distro-specific logic sits behind a thin backend interface per area (`pkg`, `firewall`, `scheduler`, …), so other distros only need new backends. Next in order: **Fedora, Arch, SUSE**. Their package data is best read through their own libraries (libdnf5, libalpm, libzypp/rpm) in separate collectors, as for Flatpak.
- **Fedora backend:** detected by the rpm database, `/usr/bin/rpm` and `/usr/bin/dnf5`. Read directly: metadata age (newest `repomd.xml` under `/var/cache/libdnf5/*/repodata/`) and automatic updates (`dnf5-automatic.timer` or its alias `dnf-automatic.timer` enabled, and `apply_updates` on; the override files `/etc/dnf/automatic.conf` and `/etc/dnf/dnf5-plugins/automatic.conf` are both reserved by the package and their precedence is unknown, so if they disagree the answer is *unknown*; otherwise the packaged default `/usr/share/dnf5/dnf5-plugins/automatic.conf`, which ships `apply_updates = no`; a timer that only downloads counts as off — verified in a Fedora 45 container). Pending updates and packages without a source come from the libdnf5 collector `gaudit-dnf-probe` (C++), which reads the system cache only (`cacheonly=all`, system cachedir also as an ordinary user), lets libdnf5 apply excludes and versionlock, and leaves install-only packages (old kernels) out of "without a source". Verified in a Fedora 45 container as root and as `nobody`, against `dnf check-upgrade` and `dnf list --extras`. Repositories live in `/usr/share/dnf5/repos.d`; local changes go in `/etc/dnf/repos.override.d`. It covers Fedora and other systems with libdnf5. The RHEL family (CentOS Stream, AlmaLinux, Rocky) still uses dnf 4/libdnf, so it gets the generic backend and the "rpm is not checked" warning until there is a dnf4 variant. The expectation is set only by `ID=fedora`, not by `ID_LIKE`, because RHEL-family systems list `fedora` there and would get a false "package system missing" warning.
- **Arch backend:** detected by package entries in `/var/lib/pacman/local` and `/usr/bin/pacman`; expected for `ID=arch` or `arch` in `ID_LIKE` (Manjaro, EndeavourOS and others use pacman). Sync database age from `/var/lib/pacman/sync/*.db`. Pending updates and foreign packages (as `pacman -Qm`) come from the libalpm collector `gaudit-pacman-probe` (C). libalpm does not read `pacman.conf`, so the collector takes the repository section names and `IgnorePkg` (globs; never counted as pending) from it; a configured repository that was never synced is an error, since every package would look foreign. Arch has no automatic updates by design; that row shows "not supported". No separate security source, so that row is not shown.
- **The backend is chosen by feature detection, never by the distribution's name.** Each backend has a `detect()` that checks for its package system (Debian: `/var/lib/dpkg/status` and `/usr/bin/dpkg`); the first one present is used, otherwise the generic backend, which knows only common program paths and Flatpak.
- **The distribution only sets an expectation.** `/etc/os-release` (fallback `/usr/lib/os-release`), read directly: `ID` or `ID_LIKE` naming `debian` or `ubuntu` means we expect dpkg/apt. If the expected package system is not found, Home shows a warning row ("This looks like Ubuntu, but its package system (dpkg/apt) was not found"); when it matches, the row is hidden and the heading is confirmation enough.
- **Recognising a distribution is not the same as being able to check it.** Each check finds out by trying, through the backend. A check the backend cannot do shows "Not supported on this system yet", which is different from *unknown* ("could not find out"). Such rows are never hidden: updates matter too much to disappear silently.
- **All package systems are detected, not just the one we check.** By their databases on disk (dpkg; rpm in `/var/lib/rpm` and `/usr/lib/sysimage/rpm`; pacman; Slackware pkgtools in `/var/lib/pkgtools/packages` and `/var/log/packages`; apk; Portage; XBPS; Nix; Guix), counting only signs of installed packages, not an empty database. Any present besides the backend's own gives a warning row ("Packages managed by rpm are not checked"), since their packages are invisible to every other check. Mixed systems happen.
- Home identifies the machine in its own group, *This computer*: one row with the host name as title and "<system> · checked as <backend>" as subtitle, e.g. "Ubuntu 26.04 LTS · checked as Debian" (nb "sjekkes som Debian"; "general checks only" for the generic backend; "Unknown system" when os-release gives nothing). The full name with version is shown, because releases go out of support. The part after the dot is how gAudit treats the system (which backend does the checks), not something read from the distribution, so it is never called a "family". It is identification, not status, so the quick checks below have their own group title, *Checks without a password*, matching *Checks that need your password*. These values come from the system and are shown as plain text, never as markup. The same goes for all row titles and subtitles on Home.
- Shipped as a regular distro package, **not** Flatpak. Its sandbox blocks the host access the app needs.

## User interface

- **Terms.** The sidebar is *sidepanel* in nb, the header bar *tittellinje*. Use these in strings and docs, consistently.
- **The program and the computer, never the name in running text (John, 2026-11-17).** Texts in the app speak of itself as *the program* (nb *programmet*) and of the machine as *the computer* (nb *datamaskinen*), relative references, never by repeating "gAudit" in row after row: an app naming itself in its own sentences reads like speaking of oneself in the third person. "gAudit" stays where a name is the point: the About dialog, the application name, the desktop file. Other programs are named, so the reader knows which one is meant ("Afterwards, the program checks that the PPA could be read for this release: add-apt-repository does not say so itself"); a name repeated sentence after sentence for what that program does gets clumsy too, so it may then be *it*, but no rule without exceptions: clarity decides. The point of all of it is that the text flows (John, 2026-11-17).
- **Planned, decided but not yet implemented** (steps 1–4 for Home are built; see *Home's groups lead to their plugin*. The page 1 → page 2 flow described below is replaced once built):
  - Home keeps *This computer*, always shown; the two groups of checks below it (today *Checks without a password* and *Checks that need your password*, and the *Checks* list) go. Right below *This computer* a dropdown sets the report level (see *Report levels* under *Plugins*). Each plugin's Home report then forms its own group: gAudit reads the report's S-expressions and builds the presentation, so a report with three sub-reports gives a group with three rows. The group's title carries the chevron to the plugin. Each plugin's report is the one closest to the chosen level: if the plugin has no report at the chosen level, the next simpler one is used (*Thorough* → *Normal* → *Quick*). A plugin with no report at or below the chosen level (e.g. only a *Thorough* one while the level is *Quick*) still gets its group, with a row saying so (implemented: "No report at this level", subtitled with the level it shows from, e.g. "Shown from Thorough", or that its check runs on the plugin's own page; the group title already names the plugin), so no plugin drops out of the list; the group's chevron still leads to the plugin. Every plugin without a core group gets a group of its own, so Home has no separate *Checks* list. A core group whose probes do not apply here (e.g. Snap without snapd) is hidden: not applicable is not the same as an empty report. The plugin's title is shown as plain text, never markup. There is no run button: the reports run when the app opens and when the user picks a level.
  - When the app opens, every report at the chosen level that needs no password runs at once, each row with its spinner (a task's `needs_admin`). Those that need it say so ("Switch to administrator to run this check"); there is no button on the row: the user switches with the header bar's switch. The group's chevron leads to the plugin's page, where the password comes only after *Run*.
  - The password is asked for only by the switch (see *Only the switch asks for the password*). Reports that need administrator rights wait as rows saying so, with the question mark, next to the user/administrator switch.
  - Almost every plugin needs administrator rights beyond Home (an exception may be backing up the user's home directory). The password dialog never opens by itself, only from the switch, so the user is not trained to type the password whenever a dialog asks for it.
  - **A plugin is a folder in the sidebar (John, 2026-11-14; navigation implemented).** Clicking a plugin in the sidebar, or its group's chevron on Home, slides the plugin's own page into the sidebar (its own `AdwNavigationView`, like folders in Secrets): a back button, then the administrator switch and the title ("Audit Center" while the content shows beside it, the plugin's name when the window is narrow and the folder shows alone), and the primary menu stays. Its first entry is *Parameters* (page 1, shown in the content at the same time); the others are its reports. **Back buttons follow the sidebar (John, 2026-11-15).** A page with an entry in the sidebar (Home, *Parameters*, *Report*) is alone at the bottom of the content and has no back button: the user moves between such pages with the sidebar, which marks where they are, and *Run* on *Parameters* changes to the report (marking *Report*) rather than going deeper. A page without an entry (a fix page, *Information*, anything further out) is pushed on top and always has a back button, back to the page it came from, whose entry is marked again: leaving a page the sidebar shows, the way back is clear and shown, which gives confidence. The folder's own back button in the sidebar leads to Home. The group's chevron on Home lands on the report entry, made from the cached collection (or, with none yet, the run under way): the Home rows are a condensate of that report. Every report made for Home is a *Simplified Report* (nb *Forenklet rapport*), at any level, since Home never uses the parameters; after *Run* on *Parameters* the entry is the *Report*. The cache keeps where its collection came from (`full`), and the entry and the content's title follow it, also while the folder is open; with nothing cached the entry is *Report*, since picking it starts the full run (John, 2026-11-14). A report entry shows the report made from the cached collection; with nothing cached it starts a run, through page 1 when the plugin takes parameters. A new collection is made by *Run* on *Parameters*. In a narrow window, a plugin opens its folder only, and the content follows when an entry is picked. The sidebar's title moves to the content: inside a plugin the content's title is "<plugin> › <page>" (e.g. "Private Files › Parameters", "Private Files › Make It Private" on a fix page; the separator is in a translatable string, so right-to-left languages can turn it).
  - **The content's header bar: Reload and the page's context menu (John, 2026-11-15; implemented).** At the end of the header bar, the context menu for the page shown (`gaudit-context-menu-symbolic`), often the same for all of a plugin's pages. On Home it holds *Information*, Home's own information page in the same shape (what Home shows, why, and how its levels, groups and password work), and *About gAudit*, as a plugin's menu holds its information and its About; no plugin entries (John, 2026-11-15). On a plugin's pages it holds *Information* and *About <plugin>*; the pages themselves are not repeated there, since the sidebar has them (keep it simple, John, 2026-11-15). *Information* pushes page 0 on top of the page shown: a page of information only, with a header (the plugin's own icon, name and short description) then three blocks, in the order what, why, how (to explain, not to persuade): *What It Does*, the general explanation of the plugin (`details`), which is the main point here; *Why It Matters*, why it matters to the user (`why`); and *How*, about the page it was opened from, set apart as a card with that page's own icon (no accent: that marks a default action), concretely: from *Parameters*, *About the Parameters* (what each of them does, the plugin's `about_parameters`); from a report, *About This Report* (what it shows, `about_report`, and whether it is the simplified one Home made, without parameters, or the full one, with the parameters as they were when it ran); plain text only; while it shows, no sidebar entry is marked, since page 0 is none of them, and going back marks the entry shown again. *About <plugin>* opens the plugin's own About dialog (`AdwAboutDialog`, as gAudit's): name, icon, short description, version, owner, license and source; the built-in plugins give gAudit's own, from `CMakeLists.txt`. *Authorize*/*Unauthorize* and *Delete* join the menu when they exist. Both sit in the menu rather than as buttons of their own: tidier at the top right (John, 2026-11-15). Beside it, to its left, Reload (`gaudit-reload-symbolic`, not mirrored for right-to-left: clockwise is a clock's way), which starts the page's current process again: on Home its checks and the reports at the chosen level (an explicit act, so the password may be asked for); on a report or a run, the collection behind it with the same parameters (the cache keeps them), a simplified one staying simplified. On *Parameters*, whose process is making the parameters, Reload sets them back: every parameter to its default, the generated ones made again (the file manager's places, none taken off the list), and the page is shown with them, with a toast saying so (John, 2026-11-15). Fix pages and *Information* have no process, so no Reload.
  - **The plugin gives the list of its reports (planned).** Not every report belongs in the folder: some are for Home only (reached there anyway), some only make sense in certain states. So the plugin gives gAudit the list of what may be listed, made dynamically from states it can find out. In a way it is a report itself, but it is never cached. Until then the folder has one fixed entry, *Report*.
  - Clicking into a plugin shows its parameters first, then a *Run* button. Run → collection → report; a run that needs administrator rights waits for the switch on the way. When the report is done the app stays on it, the plugin's folder opens in the sidebar and the report becomes its own entry there, marked as active. A fix appears in the folder only while it is available; a fix can also be linked from the report, and that link does the same as the sidebar entry.
- **One window with a sidebar** (`AdwNavigationSplitView`). The sidebar is on the left in LTR locales and on the right in RTL. GTK handles this automatically, so never hard-code left/right in icons or margins. Narrow windows show sidebar and content one at a time (breakpoint).
- **Sidebar look:** modelled on Secrets, but calmer. Each icon sits on a filled circle that is grey for pages that exist but are not shown, and accent-coloured only for the open page. Secrets gives every icon its own colour, which is too loud. Hover highlights the row only, so the accent colour always means "you are here".
- **Sidebar header:** the title "Audit Center" (nb: "Auditsenter"), also used as the window title; the app itself is still named gAudit (desktop file, About). A primary (hamburger) menu with *Preferences* and *Keyboard Shortcuts*; *About gAudit* is in Home's context menu (John, 2026-11-15).
- **Only the switch asks for the password (John, 2026-11-15; implemented).** No run opens the password dialog itself. A run that needs administrator rights, without the lease, stops before its helper part and waits, without a time limit; once per run a toast says which ("Updates needs administrator rights. Use the switch beside the title."), and the switch gets a round disc in the accent colour behind it while anything waits (not an error: it shows where the switch is). The switch is stuck at the top left, beside whatever is the title: in the sidebar's root and in each folder, also beside the back button, and, when the window is narrow (`collapsed`) and the content shows alone, in the content's header bar too, left of its title; in a wide window the content has none, so exactly one is in view (John, 2026-11-15). Clicking the switch lets every waiting run go on: the first asks for the password, the others follow within the lease. Cancelling or refusing the password ends all of them as cancelled, so the dialog's Cancel is also the way to give up on them. With nothing waiting, the switch only gets the rights. Runs as the user go on side by side meanwhile, each in its own orchestrator; only the helper's parts go one at a time, in order, through the session; runs of one plugin are one at a time (`src/gui/gaudit-session.c`). The user learns to give the password only after pressing gAudit's own button, never because a dialog appeared, which makes a password dialog faked by malware easier to tell apart. **Nothing may take focus from the password dialog (John, 2026-11-15).** A tool whose window keeps changing behind it (Software Updater's daemon opens the dialog while its window goes on updating) can take the focus mid-password, so characters are lost, or typed into another window. So gAudit never presents a window or opens a dialog by itself: dialogs only on a click, `gtk_window_present` only when the app is opened; while a run waits or goes on, only the page's content changes (rows, spinners, toasts, inline buttons such as *Keep Going*), never the focus.
- **Elevated rights are always visible (implemented):** a switch in front of "Audit Center" shows whether gAudit runs as the user (`gaudit-user-symbolic`, one person) or with administrator rights (`gaudit-superuser-symbolic`, two people, the front one in the accent colour), so it differs in shape as well as colour, with tooltips and accessible labels. Red is deliberately not used: it is ambiguous (some environments use it for a machine in the DMZ), and in gAudit it already means a serious finding. It follows the helper exactly: administrator from the helper's first line until it has ended, and always back to the user when the session ends, whatever happened, including when the lease runs out. As the user it is a button: one click asks for the password (the orchestrator's `elevate`, which starts the helper without running a check and so starts the lease). As administrator it opens a popover that explains the lease and offers *Drop Administrator Rights*, which ends it at once. *Preferences* holds gAudit's own settings only. A plugin's parameters live on its page 1, never in the Preferences dialog.
- **The sidebar** holds the Home button and the list of plugins, **one entry per plugin** (e.g. "ClamAV", "Firewall"). Each plugin is the entry point to one part of the audit. Clicking an area on Home goes to that plugin.
- **Plugins (tasks) are registered modules** with id, title, icon, short and long explanation, dependencies and parameters. Dependencies are expressed as abstract *capabilities* that the distro backend maps to paths and packages.
- **Page 1 is the main page**, to the right of the sidebar.
  - For a plugin: the parameters for *that* plugin's run. It works like a preferences window (`AdwPreferencesPage`), with a short description and a longer explanation behind "More about this". The user is not technical, so the explanations must be good.
  - For **Home**: the system **status**, meaning what can be found out *without* triggering a more extensive run. Plugins therefore need a cheap status probe in addition to the full run.
- **Page 2 is the report** produced by the selected plugin with the given parameters. The user reaches it by moving on from page 1, and it shows the progress while the report is being produced. It slides in with a back button (`AdwNavigationView`), like the legal page in an About dialog.
- **A plugin belongs to a specific tool** (e.g. ClamAV). Plugins are grouped by category (e.g. antivirus). The app scans for which tools in a category are installed, and the sidebar shows only plugins whose tool is installed. If no tool in a category is installed, that is reported on Home.
- **Status probes never need elevated privileges.** Home only reads what an ordinary user can read, so opening the app never asks for a password.
  - Probes return language-neutral results (stable id, verdict, data); the GUI turns them into text.
  - They read the filesystem directly (paths, mtimes, apt configuration), never the output of other tools.
  - When a probe cannot tell, the verdict is *unknown*, never a guess. For example, apt's nested block syntax for `APT::Periodic::Unattended-Upgrade` is not parsed and gives *unknown*.
  - Home probe for deb packages (implemented, `src/backend/ubuntu/dpkg.c`): compare `/var/lib/dpkg/status` with `/var/lib/apt/lists/*_Packages` to find (a) installed packages no software source offers (manually downloaded `.deb`s, disabled PPAs, leftovers from older releases) and (b) pending upgrades. To avoid false alarms: candidates are chosen as apt does, including apt pinning (`/etc/apt/preferences`, `preferences.d`: version, origin and release pins, specific before general, first match wins; default priorities 500, 1 for `NotAutomatic`, 100 with `ButAutomaticUpgrades`, 100 for the installed version); negative priorities are never installed, downgrades are not counted, phased updates below 100 % are held back. "Without a source" matches apt's `local` exactly, except that versioned kernel packages (kept as fallbacks) are left out. Pinning we cannot follow (regex package patterns, unknown pin types) and partly compressed indexes give *unknown*, never a guess. The "package lists" row is worded as *when updates were last checked for*, never as the system being up to date.
  - Source of security updates (Debian family, implemented): read from the Release files apt actually fetched in `/var/lib/apt/lists`, not from `sources.list`. Any `*-security` suite from a host other than the official ones (`security.ubuntu.com`, `archive.ubuntu.com`, `ports.ubuntu.com`, `esm.ubuntu.com`, `security.debian.org`, `deb.debian.org`; exact names) is a warning, because country mirrors may lag behind. No security suite at all (e.g. Debian unstable) shows no row.
  - **Packages without a source, listed (implemented):** the Home row leads to Home's page 2 with the packages in three groups, from `gaudit-orchestrator packages` (unprivileged; at most 300 sent, with a summary line that must match). *Newer than the software source* comes first: a source offers the name, but only in a lower version, so no update reaches it until the source passes that version, which may be never (bzip2 `1.0.8-6ubuntu0.1` over the archive's `1.0.8-6build2`; NVIDIA's CUDA `13.3.29-1` over Ubuntu's `13.3.29-0ubuntu1`). This is certain from the indexes. The rest is offered nowhere and is split by the maintainer in the dpkg status, a rule of thumb shown as "probably": *left over from an older release* when the distribution maintains it (an Ubuntu or Debian address, or an `Original-Maintainer`), otherwise *from other places* (a downloaded `.deb`, a source no longer set up). Fedora and Arch list them too, from their collectors' `list` mode (one `(package ...)` line each, then `(end (count N))`, parsed strictly by the shared `gaudit_collector_sourceless`; at most 512 KiB). There the leftover/other split goes by who built the package: vendor `Fedora Project`, or a packager address at `archlinux.org`. Above the source compares with the highest version any enabled repository offers for the same name and architecture (Fedora; install-only packages left out), or with the repository pacman would use (Arch). The Home count includes the packages above the source, so it always equals the list. Verified in Fedora 45 and Arch containers: a package raised from updates-testing, and one marked above its repository, land in *newer than the software source*; the counts match `dnf check-upgrade`, `dnf list --extras` and `pacman -Qm`.
  - Not done on purpose: flagging "installed version newer than any source". It would also catch packages left from an older release whose version sorts higher (bzip2 1.0.8-6ubuntu0.1 > 1.0.8-6build2), so it cannot single out a lagging mirror.
  - Flatpak (implemented): one row, shown only when Flatpak is installed. It reads local data only (no network) and counts (a) apps that are, or whose runtime is, end-of-life (fixed by the app developers, not the user) (b) unused end-of-life refs that `flatpak uninstall --unused` removes, and (c) end-of-life runtimes no app uses that `--unused` keeps because they are pinned, e.g. an old SDK left from development (both fixable by the user). All three raise a warning. It never flags ordinary updates, because Flatpak changes constantly; pending updates need the network and belong in a plugin.
  - The Flatpak data comes from a separate collector, `gaudit-flatpak-probe`, the only part of gAudit linked against libflatpak. It runs with an empty environment except `HOME`, a 5 s timeout and a 4 KiB output limit, and prints one S-expression. If it cannot start (exit 127: `libflatpak0` missing), Home shows the row with a link to the missing-software page. Built without libflatpak, or with no Flatpak installed, there is no row. The `flatpak` package does not depend on `libflatpak0`, so the library really can be missing.
  - Snap (implemented): one row, shown only when `/usr/bin/snap` exists. Data from snapd's local REST API on `/run/snapd.socket` (readable without privileges), through a separate collector `gaudit-snap-probe` (the only part linked against json-glib), with the same runner as Flatpak. Warnings: snapd not answering (nothing keeps snaps updated), automatic refreshes held system-wide, last refresh more than 7 days ago, snaps held back by the user, and snaps in `devmode` (sandbox violations only logged; not allowed in the stable channel, so almost always a leftover from testing). `classic` snaps also have no sandbox, but by design: the store reviews it and the user opts in with `--classic`, so it is shown as information only, never a warning. Ordinary updates are never flagged.
  - Collectors share one runner and one strict S-expression parser (`src/backend/collector.c`): empty environment except `HOME`, stdin/stderr on `/dev/null`, timeout, output limit, exit 127 means a missing library.
  - Private files (implemented, `src/plugins/private-files/backend/private-files.c`): known locations only, fast enough for Home. No longer a probe of Home's status: it is the Private Files plugin's quick collection (`gaudit-orchestrator secrets quick`), reported by its rule script like every level (see *Private Files* under *Built-in tasks*). Two kinds of rule. `~/.ssh` and `~/.gnupg` (with `private-keys-v1.d` and `secring.gpg`) must have the modes ssh and gpg themselves insist on, so a finding means the tool refuses or warns; the home directory must not be writable by others. Every other secret is judged by *reach*: can anyone but the owner read it through the folders on the way? A closed profile folder protects readable files inside it, and the user's own private group (same name, primary group, no other members — Ubuntu's umask 002 makes many files 0664) counts as the owner. The list covers generic credentials (`.netrc`, `.pgpass`, `.git-credentials`, `.my.cnf`, AWS, kube, Docker, gh, rclone), password stores and keyrings (pass, KWallet, GNOME Keyring, `~/.pki/nssdb`, GNOME Remote Desktop's TLS key), and the password files of Firefox, Thunderbird and Chromium-based browsers, also as Snap and Flatpak. It was derived from a deep scan of a real home directory.
  - The deep scan for secrets anywhere in the home directory (`src/plugins/private-files/backend/secret-scan.c`; developer tool `gaudit-secret-scan`) belongs in a plugin, not on Home: about 10 s on a large home. It recognises armored private keys by structure (BEGIN line at the start of a line, base64 body, matching END line), not by mentions of the markers, never reads code, documentation or media files, skips rebuildable noise folders (caches, `.git`, `node_modules`, `site-packages` …) but not the Trash, a built-in list, never one the user keeps (John, 2026-11-15: a user exclude list was considered and not wanted). It has two parts: program code and packages (`.git`, `node_modules`, `site-packages` …), always left out, and caches, left out unless the full run asks for them with *Search Caches Too* (`--with-caches`; off by default, never on Home), since a known list is also where something could hide a key; the report always says how many cache folders were not checked; a pattern with `/` matches from any folder boundary, so a copied home folder's caches are skipped and its credentials found like the real ones, and caches with names of their own (`cache2`, `Cache_Data`, `Code Cache`, `GPUCache`, `Service Worker`, `INetCache` …) are skipped anywhere, also in copies from Windows and macOS; never follows symlinks or leaves the filesystem, and reports path, mode, reason and reach, never content.
  - A Home finding can lead on: to a page explaining the problem, to the plugin that deals with it (or to choosing one, like a missing category), and always to the manual way (e.g. a copyable `chmod`). Links come from gAudit's own fixed table, never from a plugin. Whether fixing is a plugin's job or a new deliberate exception, and whether the explanation pages ship with the app, is still open.
  - Network services (implemented, `src/backend/listening.c`): distinct TCP ports in LISTEN on an address other than loopback (`127.0.0.0/8`, `::1`, `::ffff:127.x`), from `/proc/net/tcp` and `tcp6`, and how many run under the user's own account (the owner is in the file; the program needs root). Informs only, never a warning: without root, Home cannot see whether a firewall stands in front of them, and a raw port count alarms for nothing (most of a desktop's sockets are discovery and clients, e.g. Spotify, mDNS). The real finding, listening services *and* no firewall, is made by the firewall check on page 2. UDP is not counted.
  - Software outside any package manager (AppImages, unpacked tarballs in `/opt`, `~/Applications`, `~/.local/bin`) belongs in a separate *mining* plugin, not on Home. It looks only in known locations, never the whole disk, and reports "not managed, last changed …" rather than "outdated".
  - They run in `gaudit-orchestrator`, started by the GUI for each refresh (short-lived; a long-running orchestrator comes with background jobs). The probes are split into independent tasks (one task may fill several rows, e.g. pending and sourceless packages); each task runs in its own child process, side by side, so a slow one never holds up the rest. A child writes its lines with one `write()` of at most `PIPE_BUF`, so lines never mix; children die with the orchestrator (`PR_SET_PDEATHSIG`), and any still running after 50 s are killed.
  - **Each Home row has its own placeholder and spinner** and is filled in as its line arrives; rows that turn out not to apply disappear then (accepted: the page may shrink a little). The summary at the top keeps its spinner until every row has an answer.
  - The GUI starts the orchestrator with an empty environment except `HOME`, reads at most 64 KiB asynchronously with a 60 s timeout, and parses every line strictly (typed fields, text quoted with `\"` and `\\` escapes only, each kind at most once). A protocol violation (bad line, repeated kind, too much output, output ending mid-line) means nothing from that run is trusted: every row becomes unknown, including rows already shown. A row whose answer never came (timeout, a failed task) becomes unknown on its own.
- **Results from Home and page 2 agree.** Results go into the model under the task's id (one finding per check: a new result replaces the old), so the summary at the top includes them. A result from the task's own page 2 goes the same way (the session tells the controller about every result, whoever started the run), so Home and page 2 never disagree; a run that gave nothing (cancelled, refused) leaves an earlier result standing. A plugin can thus have three levels: its *Quick* rows on Home, its rows at higher levels on Home, and its full run.
- **Home's groups lead to their plugin (implemented, step 1 of the planned Home).** Home's rows are grouped by core plugin (`home_groups` in `src/gui/gaudit-window.c`, every probe in exactly one group, checked at start-up); a group is hidden once none of its rows applies. A group whose plugin this system has carries a flat chevron in its title, with the task's own tooltip ("Thorough check of the firewall"), instead of a button on a single row. The chevron is always there (John, 2026-11-15): with a collection cached it lands on the report made from it; with none yet but the plugin's run under way (e.g. Home's at start-up), on page 2 following that run (`gaudit_run_page_follow`), which shows its result when it is done; otherwise as the report entry does (a run, or *Parameters* when the plugin takes them). The sidebar entry stays as it is for now. Each task has exactly one row, in its plugin's group, so nothing is listed twice ("A firewall is installed" next to "Not run yet" in another list would contradict it). The *Report Level* dropdown (setting `home-level`, default `quick`) sits right below *This computer* (step 2, implemented): a task's `home_level` (firewall rules *Normal*, package files *Thorough*) puts it as a row in its group at that level and above; once it has a result in this session the row stays, also at a lower level. Opening the app, Reload and picking a level run the level's tasks one after another (`app.run-level`), those that need no password first, so one waiting for administrator rights never holds up the others; every task waiting its turn shows its spinner from the start and loses it only when its own run is done, the one waiting for the switch shows the question mark, and when the queue stops early (a cancelled or refused password) those still waiting say why (John, 2026-11-15). A level picked, or Reload, while a queue waits for the password stops that queue and starts over. A cancelled or refused password stops the rest. The status-ok shield means every task at the chosen level ran and passed; at *Quick* there are none, so it stays at high.
- **Home has its own page 2 for a missing category.** If no tool in a category is installed, Home shows it as a finding (e.g. "No antivirus program found") with a "Choose one" button. It opens a Home-specific page 2 listing the known plugins in that category, each with an explanation and the install command, and one marked as recommended. This keeps uninstalled tools out of the sidebar. The recommended tool is marked with an icon and "Recommended" in plain colours: a filled or accent-coloured badge reads as a button, and it is not one. (Implemented for firewall and antivirus, `src/gui/gaudit-category.c`: the Home row "No firewall found" or "No antivirus program found" leads to it, and so does the firewall's page 2 when no firewall program is installed. Which tools a category has and what they are is presentation in the GUI; package names and the install command come from the backend's fixed table, and only tools the backend knows how to install are shown. The backend's `recommended` list marks the distribution's usual choice, shown first: ufw on Debian, Ubuntu and Arch, firewalld on Fedora. After installing, the tool's fixed enable command follows, since an installed firewall is not necessarily switched on. The install button comes with PackageKit; until then the commands are copyable only.) The plugin "software is missing" page is then only for a *partially* installed tool (e.g. ClamAV without `freshclam`).
- **Long runs as the user (John, 2026-11-14; implemented).** Home's runs keep a hard limit (5 min). The full run (with the plugin's parameters, e.g. large or network folders) has none: the collection prints `(progress (count N) (where "..."))` at most every 2 s (entries looked at, and the folder being searched, "~" for home; not part of the collection, at most 1 MiB of output for such a run), page 2 shows "Looked at N files and folders so far · now in /mnt/backup/old-copies" so the user sees it is alive and roughly where it is slow (the folder shown is the stem the folder now and the folder at the last report share, so a search that stays in one tree narrows to it), and after 10 minutes asks "The search is taking a long time. Keep going?" (*Stop* and *Keep Going* side by side, the default at the end; *Keep Going* asks again 10 minutes later); the search goes on while it asks, and goes on to the end if the page is left. A stopped search says so, suggesting fewer folders. After each folder the collection gives `(area-stats (index I) (entries N) (seconds T) (truncated 0|1))`, and the rule names the folder where the search stopped at its limit, and an added folder that is large or slow (thresholds in the rule: 250 000 entries, 10 minutes), suggesting it off the list. A second parameter, *Read Files Up To* (16 KiB, 64 KiB, 256 KiB, 1 MiB; default 64 KiB, which Home always uses): files up to that size have their start read to recognise a key, larger ones are judged by name only. Nothing lower than 16 KiB is offered, since every real key file is far smaller; a lower limit is faster on large, slow disks. It goes to the collection as `--read-limit=N` (the orchestrator takes only the listed sizes), and the report says so when it is not the default (John, 2026-11-15). The limit of 500 000 entries stays for every folder, the home folder too (John, 2026-11-15: it may change, but makes sense for now).
- **Closing ends the app (John, 2026-11-15; implemented).** The window's close button closes, and with the last window the app ends: runs under way stop, the elevated session ends. Only when a run has gone on for more than 10 seconds is the user asked first ("Stop the Check and Close?", *Stop and Close* or *Cancel*). Ctrl-C (SIGINT) and SIGTERM end at once, without asking. Every orchestrator dies with the GUI that started it (`PR_SET_PDEATHSIG`), however the GUI ends, so no search is left running without an owner. The planned three-way dialog with *Keep running in the background* comes with background jobs.
- **Run while an earlier run is still going (John, 2026-11-14; implemented, `src/gui/gaudit-run-page.c`).** A general method for every plugin. Pressing *Run* on *Parameters* while a run is under way (e.g. Home's collection at start-up): with the same parameters, page 2 says "In progress, processing…" and shows that run's result when it is done; with different ones (for a collection, a different depth counts), it asks "In progress, restart?" with *Stop and Restart* and *Wait*, and this page's own run starts once the other has ended. So a long run, or one out of control, can be stopped. Runs of different plugins go side by side; this is about another run of the same plugin. The session can say which run of a plugin is under way (`gaudit_session_running_for`), let more than one wait for it (`gaudit_session_attach`) and stop it (`gaudit_session_cancel_for`, ending as cancelled): a run as the user stops at once; one through the helper ends the session, at once while the password is asked for, but once the helper is root only after the check under way, since it cannot be killed from the user's side (each check has its own limit). Home's row then says it was stopped.
- **Jobs keep running when the user leaves page 2,** and also when the window is closed. When a job finishes, the app shows an in-app toast that stays until dismissed (no timeout). The start button stays a start button: going into the plugin and starting it runs the check again, and the new result may differ.
- **Results of heavy checks are kept for the session (implemented for tasks listed under Home's *Checks*):** the latest result of each run, whoever started it, updates its Home row: the verdict as the icon on the left (a check mark when all is well) and what was found with the time ("No changed package files found · checked at 14:32"; per row, since these run one by one). It counts in Home's summary, since a plugin may make the overall status worse. It lives until the app closes; nothing is stored on disk yet.
- **By default, finished jobs are reported only with in-app toasts.**
- **Closing the window while jobs are running** brings up a dialog (`AdwAlertDialog`) with three choices:
  - *Keep running in the background:* the app stays alive without a window until the jobs finish, then exits.
  - *Stop the jobs and close:* running jobs are cancelled and recorded as cancelled in the history.
  - *Cancel:* the window stays open.
- **System notifications are used only for jobs that finish in the background**, and are kept tidy. Notifications nobody cleans up are not allowed.
  - There is at most one notification, with a fixed ID: "N unread reports".
  - It is replaced as the count changes and withdrawn when every report has been read.
  - It has a button that opens the app (as does clicking the notification itself). If all unread reports belong to one plugin, the app opens on that plugin; otherwise it opens on Home.
  - When the app is opened again, the notification is withdrawn and unread reports are shown as toasts.
- **Unread markers.** A plugin with unread reports gets a marker (badge with count) in the sidebar and on its Home row, and unread runs are marked in the history list. A report counts as read when it has been opened on page 2.
- **Reports are kept.** Like Pika Backup, page 1 points to a list of earlier runs with their status, and each run opens its report.
  - The stored format is structured data (S-expressions), and page 2 is built directly from it.
  - Markdown is produced only when a report is exported, so it never needs to be parsed.
  - Reports are stored in `~/.local/share/gaudit/reports/` with mode `0600`, because they contain system information.
  - The user's area can be modified by malware on the account, so the history is compared with the helper's root-owned log, and reports that do not match are marked.
- **A plugin can produce several reports.** Page 1 is then divided into one section per report, each with its own parameters and its own start button. Each run opens its own page 2.
- **Parameters are remembered in GSettings.**
  - Plugins cannot install their own schemas, because a schema with our ID could override ours. gaudit ships one relocatable schema, and each report gets its own path: `/io/github/jeblad/gaudit/plugins/<plugin-id>/<report-id>/`. Values are validated against the plugin's description when read.
  - dconf is writable by the user, so a compromised account can switch checks off silently. Therefore every report states which checks were switched off, and Home shows it as a finding.
- **Missing dependencies:** the app shows an explanation and the install command in a read-only field whose text can be selected and copied. The field has a copy button and an install button. Many people are not comfortable running an installation they do not understand, so the manual field must always be there. The command is always shown LTR, as plain text (no markup, no mnemonics).
  - The command text is never selected in advance (`gtk-label-select-on-focus` off): the user expects to select it, and a ready-made selection only has to be undone first.
  - **What you see is what you get.** The copy button copies the text in the field as shown, never data kept beside it, and first compares it with the command the field was made from; if they differ, nothing is copied. The install button will do the same check before installing, with the package names still taken from the backend's fixed table, never parsed from the field. This raises the bar, nothing more: code running inside the GUI process can still change the field and the data together, or act between the check and the click. The real defence is keeping foreign code out of the process (see *Threat model*), and for installing, the helper re-checking the packages against its own table.
- **Installation:**
  - Primary: **PackageKit** (D-Bus).
  - Fallback: `pkexec` with the backend's fixed argv (`/usr/bin/apt-get install -- <packages>`), run with `execve`. The UI must then state clearly that the fallback is used.
  - Package names always come from the backend's fixed table, never from text that can be manipulated.
- **The availability check in the GUI is for user experience only.** It decides what is shown; the helper re-checks everything and decides.

## Plugins

The app can be extended with new audit methods, but an extension must never be able to change existing methods. That cannot be guaranteed when plugin code runs in the same process, so the boundary is between processes and data:

- **No plugin code is loaded into the GUI or the helper** (no `dlopen`). A plugin consists of:
  - a declarative description: id, title, explanations, parameters, capabilities and translations. The GUI builds pages generically from it.
  - a collector: a separate program the helper starts with privileges dropped. It uses the same protocol as the built-in checks.
  - Guile rules that run in the playpen, in their own environment.
- **Namespaces.** `core.*` is reserved for the core key. Each owner has its own namespace and cannot use others'. The registry rejects an id that already exists, and any attempt to override.
- **Plugins can only add.** A plugin can add findings and make the overall status worse. It can never hide, change or downgrade others' findings.
- **Privileges are declared.** The helper never gives a collector more than its description states.
- **System-wide and root-owned only** (`/usr/share/gaudit/plugins/`). Plugins in the user's area are never loaded.
- The built-in tasks should use the same format, marked `core`, so there is only one code path to keep secure.
- **Authorization.** Our own plugins and plugins from owners on the signed trust list are authorized by that list, however they were obtained. Authorization follows from the signature and the list, never from the download path. Any plugin, whatever its origin, can be deauthorized by the user. That only removes the user's own access to run it.
  - *Authorize*, *Unauthorize* and *Delete* all go through the helper and require the administrator password. Switching a check off is exactly what malware would want to do.
  - Home always shows a deauthorized plugin as a finding (e.g. "ClamAV is not authorized"), so the change is never invisible.
  - Reports are kept when a plugin is deauthorized.
- **Semi-blocked plugins and local approval.** Every plugin whose owner is not on the signed trust list is semi-blocked: the user may download it, but it is not loaded until the user approves it locally. A locally approved plugin is loaded, and it is marked "locally approved" wherever it appears, including the sidebar, page 0 and its findings.
  - Approval goes through the helper and requires the administrator password (polkit `auth_admin`), so malware on the user account cannot approve its own plugin.
  - Approvals are stored root-owned (`/etc/gaudit/approved-plugins`). Each approval binds the owner's key, plugin id, version and digest, so a new version must be approved again.
  - After approval, the helper installs the plugin root-owned, even if the user downloaded it to their own area.
  - All other plugin rules still apply: own namespace, add-only findings, declared privileges.
- **Plugin menu.** The content header, next to the window buttons, has a ⋮ menu (`view-more-symbolic`) for the plugin being shown. It holds *Authorize*/*Unauthorize* (the label follows the state), *Delete*, and an item that reopens page 0. Home has no plugin menu.
- **Page 0 – about the plugin.** It is shown while a plugin is not authorized (the plugin cannot run until it is), and the first time an authorized plugin is opened. gAudit renders it from the plugin description, as plain text only: no markup and no links, so a plugin cannot imitate gAudit's own UI. A button leads on to page 1.
- **Plugin legal information lives on page 0, not in gAudit's About dialog.** The plugin's page 0 text must include its license, copyright and owner, so the About dialog does not fill up with plugin sections. Libraries are never listed, neither a plugin's nor gAudit's own: traversing the dependency tree would be far too extensive.
- **Plugin licensing is open.** A plugin may use any license, compatible with GPL or not. gAudit does not police this. Plugins talk to gAudit only through processes and data (the description format and the pipe protocol), never by linking, so the formats should be documented as a public interface. Security stays closed by default (see the trust list); "open" here means licensing only.
- Deliberate limitation: complex, custom actions in the UI are not possible. Parameter types are extended as needed (switch, choice, path, …).

### Plugins, profiles and data flow

- **Fixes are not in the report (John, 2026-11-14).** Page 2 is a report: every row carries its verdict as a symbol (warning where something is wrong, the check mark where it is fine), so a problem stands out. A row with a problem has a chevron that leads to a page with the fix for exactly that problem (`gaudit_fix_page_new`: what is wrong, what to do, the manual command, a note). The report never lists commands itself, so it does not overflow, and the same fix page can be reached from anywhere. Done for Private Files; package integrity's reinstall command and the firewall's enable command still sit on page 2 and should move.
- **gAudit checks for itself; admin tools get sub-plugins (John, 2026-11-15).** A plugin's checks, and what Home shows for it, read the effect on the system directly (for updates: apt's effective settings, the timers, when they last ran, pending security updates) and never depend on which admin tool, usually a graphical one, the user has. Whether such a tool is in use is a check of its own: each known tool (Software Updater, Synaptic, App Center, …) has a sub-plugin, an extra entry in the plugin's folder in the sidebar, shown only when the tool is installed (found through the package database). It checks that the tool does what it should (its settings are the ones in effect, nothing overrides them) and does most of the work of the fixes in that tool's terms. Tools come and go (Canonical plans to retire Software Updater), so knowledge of one tool lives in its sub-plugin, never in the plugin's own checks. For automatic updates this means: warn when checking for updates is set to never, and always when security updates are pending (John, 2026-11-15; replaces an earlier grace of a day after an automatic run); other updates waiting are a warning when nothing installs them automatically and nothing has been installed for more than two weeks. Automatic installation switched off is a *recommendation*, not a warning: there may be a reason for it, so gAudit does not nag. A setting that only downloads or only shows security updates is not a warning on its own. A sub-plugin is a plugin of its own, with its own namespace, importing what its plugin exports (e.g. `core.updates`), so others can make sub-plugins for their tools (John, 2026-11-15).
- **One problem, one page 3 (John, 2026-11-15).** Each row on page 2 that leads on has a page 3 that solves the problem of that row and nothing else, so no page grows large and hard to follow: the three groups of packages without a source are three pages, each listing its own group, not one page with three groups. Rows share a page only when they have the very same fix (e.g. every changed or missing package file to one reinstall page, both daily jobs to one page that switches them on).
- **A software source set up but never read is a warning (John, 2026-11-15; implemented for Debian and Ubuntu).** Found when keybase sat among the packages from other places although its source was set up: apt had never fetched its lists, often after an upgrade of the release or when a source is added without looking for updates since, and nothing from it got updates. The collection compares the sources set up (`/etc/apt/sources.list`, `sources.list.d/*.list` and `*.sources`, both formats; `deb-src`, `Enabled: no` and `cdrom:` left out) with the Release files apt fetched (the list file names start with the URI without its method, credentials and trailing slash, `/` as `_`); a `deb` entry that cannot be read gives *unknown*, never a guess. This reads `sources.list`, unlike the source of security updates, which reads only what was fetched: here what is set up is the point. Its row under *Where updates come from* names the hosts and leads to *Read the Software Source*, whose step is `apt-get update`, which shows why a source cannot be read (often a signing key missing or expired). The text for packages from other places says only what gAudit knows: no source it fetched lists from offers them, which may be a downloaded package or a source that cannot be read, never that they are abandoned.
- **Sources switched off at an upgrade of the release (John, 2026-11-15; implemented for Ubuntu).** Ubuntu's upgrade switches off third-party sources (`Enabled: no`, or the deb line commented out) and keeps a copy beside the file (`<name>.distUpgrade`); that copy is the sign, so a source switched off by hand does not count. A source that is on in another file no longer counts either: `add-apt-repository` sets a PPA up in a new file named after the release running (`…-stonking.sources`) and leaves the old one off with its copy (seen on John's machine, 2026-11-15), so the PPA has been set up again. Under *Where updates come from* they are a recommendation, never a warning, since it was done on purpose: a source may not have packages for the new release yet, and switching it on then only gives an error at the next look for updates (as with the PPAs John met). Shown by the name people know (`ppa:owner/name` for a PPA, else the host); the page says to check the source's own page (Launchpad for a PPA) before switching it on. A PPA gets a step on the page, with copy and run (John, 2026-11-15): `sudo add-apt-repository -y ppa:owner/name` (operation `add-ppa` in `common/apt-ops.h`; one step per PPA, at most four, shown only when `/usr/bin/add-apt-repository` exists), which sets it up for the release running, with its signing key from Launchpad, and fetches the lists; the note says that Launchpad must list packages for exactly this release before it is run: packages for older releases are not enough, and neither is the release listed without packages (wireshark-dev/stable had `stonking` with empty lists). `add-apt-repository` ends with 0 even when apt cannot read the PPA (a 404 for its Release file, checked on 26.10), so afterwards the helper checks that the PPA's `InRelease` or `Release` for the release running (`VERSION_CODENAME`) is in `/var/lib/apt/lists`, and reports 100, apt's own code for an error, when it is not (`gaudit_apt_ppa_read`). If it stops with an error, the step says so in its own words (`GauditFixStep.failed`): the PPA most likely has nothing for this release yet, is now set up and gives the same error at every look for updates, and is switched off again under *Other Software* in Software & Updates; gAudit does not switch it off, since the file is not its own (makemkv-beta on 26.10, John, 2026-11-15). The name is checked as plain (`ppa:` then owner and name, `[a-z0-9][a-z0-9+.-]*`) by the GUI, the orchestrator and the helper, and the helper runs it only for a PPA named by a file in `/etc/apt/sources.list.d` that has the upgrade's `.distUpgrade` copy beside it (`gaudit_apt_ppa_ok`), so within a lease nothing on the user's side can have a PPA of its own choosing added as root: only one this computer had before. Other sources are switched on in the system's settings; gAudit does not do it for them. A package's version may name the release it was built for (`~ubuntu25.10.1`, `ubuntu0.24.04.1`, `+deb12u1`); when that is older than the release running (os-release), its row says "built for Ubuntu 25.10". A package built for an older release is tied to the sources switched off at an upgrade that were for that release (the suite in the switched-off file, `questing`, to its version by distro-info's table, `/usr/share/distro-info/ubuntu.csv` or `debian.csv`): its row then says "probably from ppa:cappelikan/ppa, switched off when the release was upgraded". Never certain, since dpkg keeps no origin; several matches are all named, none says nothing (John, 2026-11-15).
- **What helps judge a package without a source (John, 2026-11-15; implemented for Debian and Ubuntu).** Removing one can break something, and a downloaded or locally built package may sit among the leftovers by its maintainer, so each package in the lists shows what can be found out, never advice: probably replaced by a Flatpak app (an AppStream metainfo or desktop file id it installed, found as a Flatpak app id in `/var/lib/flatpak/app` or the user's own) or a snap (that id, or the package's name, under `/snap`); how many installed packages depend on it (Depends and Pre-Depends, any alternative) and the first of them, worded as only what was seen ("no other package depends on it", never "nothing needs it") and left out at zero for a program, a package with a desktop entry, which people start themselves (John, 2026-11-15); installed on purpose or as a dependency (`/var/lib/apt/extended_states`; a package installed with dpkg alone counts as on purpose); when it was last installed or upgraded (its file list's time). All read as the user (`gaudit_deb_package_details`), sent with each `(package ...)` line, and libraries without a desktop entry are never matched to a Flatpak or snap. Where it came from (apt's history, which rotates) is not used yet.
- **Known vendor packages without a source (John, 2026-11-16; steps 1 and 2 implemented: recognising and showing them, and looking for the newest version).** The table is `src/plugins/updates/common/vendor.{h,c}` (Zoom first); the Updates collection takes a package that matches by name and maker (Maintainer up to " <", read by `package_details`) out of the groups and the list of packages without a source, counts it as `sourceless-vendor` and sends a `(vendor-package (id …) (title …) (vendor …) (version …))` line each; the GUI accepts only ids in the table and builds the page from the table, never from the line. Step 2 is implemented (John, 2026-11-16): *Check for a New Version* runs `gaudit-orchestrator updates latest <id>` as the user, which asks the table's `latest` address for its response headers only, with `/usr/bin/wget` if it is there, else `/usr/bin/curl` (fixed argv, no configuration file, https only, no redirect followed, an empty environment but `LC_ALL=C`, 30 s), and takes the version from the redirect only when it is exactly the table's prefix, digits and single dots, and suffix (Zoom: `https://cdn.zoom.us/prod/7.2.5.6661/zoom_amd64.deb`, one small request, nothing downloaded). It compares with the installed version by the package system's rules (`version_compare`) and writes `(vendor-latest (id …) (status 0|1) (version …) (installed …) (newer 0|1))`, which the GUI puts into the cached collection before its closing line, so the report and Home follow; the version from the network only decides what is shown. The page is clear that this is a fallback (John, 2026-11-16): a software source is better, since the system then updates the program with everything else, from the vendor itself or from someone the user trusts; gAudit names no such source, and says that a source's key decides what is installed, so the choice is the user's. The check stays on the package's own page, one click away, on purpose (John, 2026-11-16): never on Home or when the app opens, which would also be the network unasked; that it takes a click is a friendly nudge, so a downloaded package does not feel as easy as one from a source. Step 3 (installing; John, 2026-11-16; implemented): once a newer version is known, the page says so in a paragraph followed by *Install* (never *Upgrade*: upgrade and update run together for users), and *Check for a New Version* goes grey. *Install* downloads and verifies; when the signature is weaker than expected, a paragraph says what and *Install Anyway* follows, with no *Cancel*, since the back button is the way out. The page then says it went well, or gives the error, and the button used goes grey either way. How it runs: `gaudit-orchestrator updates download <id> <version>` downloads, as the user, from the table's prefix, version and suffix (wget, else curl; https only, no redirect, no configuration file; at most 1 GiB) into `~/.cache/gaudit/vendor/<id>.deb`, after emptying that folder. Then `run vendor-verify <id> <version> <path>` in the helper (root with only CAP_DAC_READ_SEARCH, in the sandbox): it copies the download, opened without following any link, into `/var/cache/gaudit/vendor/` (0700, emptied first), and checks that copy: an ar archive of exactly `debian-binary`, `control.tar.*`, `data.tar.*` and `_gpgbuilder`; `sqv` (Sequoia, in Rust, the verifier apt itself uses on newer releases; John, 2026-11-16) with the vendor's key file from `GAUDIT_VENDOR_KEYS_DIR` (root-owned and not writable by others outside developer builds), strict first: a signature its default policy accepts is *verified*; one it accepts only with gAudit's own policy file `sha1-only.toml` (beside the keys, the same rules; SHA-1 allowed for signatures, nothing else weaker) is *weak*; anything else is refused. Only what `sqv` authenticated is read on, and only when it exits 0 (it writes its output even when it refuses): the one key's fingerprint it names, which must be in the table, and the text it wrote, Role builder, its Files listing every part with matching MD5, SHA-1 and size; gAudit no longer parses the signature file itself; `dpkg-deb --field` giving the table's package name and the version asked for; that version newer than the installed one (`dpkg-query`, `dpkg --compare-versions`). It writes a mark with the copy's SHA-256, and `run vendor-install <id> [anyway]` installs only that copy, still the same bytes, with `apt-get install` (*anyway* is needed when the signature was weak), then removes it. The download is removed once checked, when the page closes and at start-up; the helper's copy after installing, before each check and when the session ends, and an empty folder is removed too. Results are `(vendor (id) (action verify|install) (result …) (version) (hash))`; the page says each in gAudit's own words. Checked against Zoom's real package (2026-11-16): `weak`, SHA1; a byte changed gives `mismatch`. The vendor keys are armored in `src/plugins/updates/keys/` and dearmored at build time; `tests/test_vendor.c` holds the key file's fingerprint equal to the table's. Some vendors offer only a `.deb` to download and no software source (Zoom, and likely Discord and Obsidian), so the package never gets updates through the system. A fixed table of gAudit's own recognises them by package name *and* vendor (`Maintainer:` in the dpkg status, so another package with the same name is not taken for it) and its row says what is known: the vendor offers no source, new versions are downloaded from the vendor's site, the version installed. The recommended way is a Flatpak or snap where a ready one exists, saying who makes it (the table keeps Flathub's mark for each Flatpak, checked by hand with where and when, like the keys: Zoom's `us.zoom.Zoom` is *Unverified*, 2026-11-17, so the page says someone other than Zoom makes it; with no mark checked, the page says what the marks mean) (Flathub's *Verified* mark, never what other pages call it); AUR on Arch is named at most, never recommended, since anyone can put packages there unreviewed. Third-party apt sources that mirror a vendor's package (one person's key signing what is installed as root) are never suggested; one the user has set up is a source like any other. The user chose the `.deb`, so gAudit helps and warns: a page with explicit *Run* may download the vendor's package from the table's fixed address and check whether it is newer than the one installed, and install it only when it is signed and the signature checks against the vendor's key in gAudit's table: an unsigned package cannot tell who sent it, so it is never installed (it may be shown as newer, with the download left to the user). A signature that checks but is weaker than expected (Zoom signs with `dpkg-sig` over SHA-1, with MD5 and SHA-1 for the parts, checked 2026-11-16 against the key on Zoom's download page) is the user's choice (John, 2026-11-16): the page says what was checked (the vendor's key by name and fingerprint, the contents matching) and what is weaker, in plain words (an older method that apt no longer accepts for software sources), with *Install Anyway* (the back button is the way out); without gAudit the user would install it with no check at all. Never a choice: unsigned, another key, a bad signature, contents that do not match, or a signature resting on MD5 alone. The table keeps each vendor's keys with the first version each signs, since vendors change keys and announce it (Zoom: `84C3 65D6 CC9A 4886 CA92 6BCC 4F21 9739 9706 AC24` from version 6.7.5). Only keys for versions gAudit may install: an older key is left out, since nothing older than what is installed is ever installed, and gAudit vouches for as few keys as it can (John, 2026-11-16). A vendor key nobody else vouches for (self-signed, no web of trust) is taken only by its fingerprint in gAudit's table, and putting it there is gAudit vouching that the key is the vendor's, nothing about the software (as with the trust list: we do not audit). So the table is listed in the signed manifest like gAudit's own code, each key with where and when its fingerprint was taken (e.g. Zoom's download page, 2026-11-16), and only a few vendors common enough to be worth it are taken in; Zoom is one (John, 2026-11-16). In the report they are a group of their own (John, 2026-11-16), under *Where updates come from*, e.g. *Programs You Update Yourself*: one row per package (name, vendor, version installed), taken out of *from other places* so nothing is counted twice, each leading to its own page with more text (why it gets no updates, what gAudit can check, a Flatpak or snap and who makes it) and buttons that say exactly what they do: *Check for a New Version* (downloads from the vendor's fixed address as the user and compares versions, installs nothing) and *Install*, available only once a newer, verified package is downloaded (*Install Anyway*, with the explanation, when the signature is weaker than expected). The rows are recommendations and never reach Home, since without the network gAudit knows only that the system does not update the package, not that it is out of date; once *Check for a New Version* has found a newer one in this session, its row is a warning and reaches Home. The helper checks with `/usr/bin/sqv`, a fixed argv and the vendor's key from the table as its only keyring, since libsodium has no RSA or OpenPGP; without `sqv` nothing is installed. The download runs as the user (the helper has no network); the helper copies the file into a root-owned place, checks the signature on those same bytes and installs that copy, so nothing on the user's side can swap it in between. makemkv (`makemkv-oss`, `makemkv-bin` from a PPA with nothing for the release) is put off for now. Discord is in the table without a key (John, 2026-11-16): its `latest` address redirects to `…/linux/x64/<version>/Discord.deb`, `Maintainer: Discord Maintainer Team`, but it signs nothing (no `_gpgbuilder`, nothing beside the package; checked on 1.0.169), so its page may say a newer version is out and where to get it, says plainly that Discord does not sign its package so gAudit cannot check who made it, and never offers *Install*; the orchestrator refuses to download for a vendor without a key, and the helper to check one. Its `postinst` (root, `rm -rf` through each `/home/*/.config/discord/…`, links in users' folders followed; `pkill Discord` for every user) was reported to Discord (support request #69969725, 2026-11-16) rather than noted on the page: a note bound to one version of a vendor's script goes stale, and gAudit does not check the script itself. **Obsidian** is in the table without a key too (John, 2026-11-17: common enough to include): `Maintainer: Dynalist Inc.` with no address, `obsidian_<version>_amd64.deb` on GitHub with no signature in the package or beside it (checked on 1.15.1); its newest version is the release tag GitHub's `releases/latest` redirects to (`…/releases/tag/v1.15.1`, empty suffix). Its install scripts are an ordinary Electron install (the `/usr/bin` link, the sandbox helper, an AppArmor profile) and touch no user's folder. Its own snap (`obsidian`, published by Obsidian) is named first, then the Flatpak `md.obsidian.Obsidian`, which Flathub has verified through `obsidian.md`; the table names a snap only when the vendor publishes it. Flathub's marks are read from its public API (`flathub.org/api/v2/appstream/<id>`, `flathub::verification::verified`), not guessed from what a page or a person calls it (2026-11-17: Obsidian's and Discord's are verified, Zoom's is not). *Verified* is said as Flathub defines it, "published by the original developer or an authorized party", never as "the maker builds it": Obsidian calls its Flatpak community maintained, yet it is verified (John, 2026-11-17).
- **Local copies of a vendor's source (John, 2026-11-16; implemented for NVIDIA's CUDA).** Built as: a second table in `common/vendor.c` (`gaudit_vendor_local`: folder pattern in /var, product, vendor, download page, the versioned package's prefix, and the releases with a network source, checked for x86_64 at developer.download.nvidia.com on 2026-11-16: ubuntu2004, 2204, 2404, 2604, debian11–13; none for 2504, 2510, 2610); the Updates collection reads each such folder's own `Packages` index (plain; a folder without one is not counted) through the backend's `each_package`, counts the installed packages with the very name and version it lists, and the installer's own package, whose name is the folder's (`cuda-repo-ubuntu2604-13-3-local`, installed with `dpkg -i`, not in the copy's index), takes those out of the groups of packages without a source and of their list (counted in `sourceless-vendor`), and sends `(vendor-local (id) (title) (vendor) (version) (made-for) (made-for-name) (running) (previous) (packages))`, the release before from distro-info's table. Its page (`vendor_local_page`) is built from the table, never from the line's texts. A vendor's "local" installer sets up a `file:` source on the disk that never changes, with its own key (NVIDIA's CUDA *deb (local)*: `/var/cuda-repo-<distro><version>-<cuda version>-local`, seen as `ubuntu2604-13-3-local` on a 26.10 machine), so what it installed never gets updates and may be built for an older release; its packages can also sort above the distribution's own (`13.3.29-1` over Ubuntu's `13.3.29-0ubuntu1`), so neither source updates them. A second kind in gAudit's vendor table recognises such a source by its pattern and shows it as one row for the product with its package count under *Programs you update yourself* (a recommendation, never on Home: staying on a version can be deliberate, e.g. for a development project), not a row per package. Its page recommends the vendor's network source (NVIDIA's `cuda-keyring`) when gAudit's table lists one for exactly the release running; NVIDIA's versioned packages (`cuda-toolkit-13-3`) keep a toolkit on its version while still getting its fixes (to be checked against NVIDIA's source before the page says so). Strict by default: with no source for the release running, the page says so, and only on an explicit click on the page (never a stored setting) shows the one for the release before, never further back, since NVIDIA's toolkits are often forgiving about the release. Using a package or source made for an earlier release is not something gAudit recommends, and the page says so plainly (John, 2026-11-16): it was made and tested for another release, against the libraries that one has; said as what it is, not as a level of danger (see *No threat levels*), and the choice stays the user's. gAudit never downloads or installs anything for it. The list of releases a vendor has a network source for is kept by hand in the table, like the keys. A *runfile* install (outside dpkg, `/usr/local/cuda-*`) belongs to the planned plugin for software outside any package manager.
- **Packages another program keeps up to date (John, 2026-11-16; implemented).** Some programs install a package on the host themselves and replace it when they are updated, so it has a source, only not apt: ClamUI's `clamui-privileged-helper` (`Maintainer: ClamUI Contributors`), which ClamUI's *Install Helper* downloads from its GitHub release, checks and installs through polkit, and which must match ClamUI's own version. A third kind in the vendor table (`gaudit_vendor_companion`: package, maker, the managing program, its Flatpak app id and its own package) recognises it by name and maker; the collection takes it out of the groups of packages without a source and their list, checks whether the managing program is installed (its Flatpak app for the system or the user, or its package), and sends `(vendor-companion (id) (package) (manager) (version) (present 0|1))`. Under *Programs you update yourself* it is a row that is fine ("kept up to date by ClamUI") while the program is there, and a recommendation ("installed by ClamUI, which is no longer here · nothing updates it now") when it is gone. A helper built locally from a clone has the same name and maker, and cannot be told apart.
- **Updates kept from the release before (John, 2026-11-16; implemented for Debian and Ubuntu).** An update the distribution made for the release before (`libx11-6 2:1.8.13-1ubuntu0.1`, in 26.04's `-security` and `-updates`) stays after an upgrade when the new release ships an older version (26.10 has `2:1.8.13-1` and no update yet, checked 2026-11-16): it is newer than the source, but it is not a problem, and often carries a fix the new release lacks. The dpkg scan puts such a package in a fourth group, `GAUDIT_SOURCELESS_KEPT` (the Debian backend's own; collectors give the first three only), when it is above the source, by the distribution, versioned as an update after a release (`ubuntu0.<digit>`, `+deb<N>u<digit>`) and last installed before the release was last upgraded, taken as when `base-files` was last installed (its file list's time in `/var/lib/dpkg/info`, readable by the user). Always "probably": dpkg keeps no origin, and whether it was a security fix or a bug fix cannot be told from here (the version is the same shape for both, and the release before's lists are gone after the upgrade), so the text says it may be either (John, 2026-11-16). In the Updates report it is a recommendation, never a warning, with the release before by name (`sourceless-kept`, from distro-info's table), leading to its own list page *Updates kept from the release before*; Home's count of packages without updates leaves it out.
- **Where a package came from, recorded at install time (John, 2026-11-16; planned, not built).** apt and dpkg keep what was installed and when (`/var/log/apt/history.log`, `/var/log/dpkg.log`, rotated away after about a year), but never which software source a version came from, which is why gAudit says "probably" about packages without a source. A deliberate exception, judged legitimate (John, 2026-11-16): the gAudit package installs a drop-in in `/etc/apt/apt.conf.d/` that has apt run a small program, `gaudit-apt-origin`, before dpkg installs (`DPkg::Pre-Install-Pkgs`, protocol version 3; its exact format to be checked first). For each new package version it looks up which sources offer that very version in apt's lists at that moment, or notes that it came from a file on disk (`apt install ./x.deb`), and appends one line (time, name, architecture, version, origin) to a root-owned log readable by all (`/var/lib/gaudit/origins`; it says no more than the dpkg status and the source lists already do). It always exits 0 with a short time limit, so it can never stop or slow an install, and is kept as small and strict as the helper, in C. A switch turns it off for those who find it a problem: not in dconf, which malware on the account could change, but a root-owned file (`/etc/gaudit/apt-origin`) written and removed through the helper with the password, as gAudit's own setting for automatic updates is; while it is off, Updates says so as a recommendation, so the change is never invisible. With a record, "probably from other places" can become "installed from a downloaded file on <date>" and "kept from the release before" certain, for what is installed after gAudit came; earlier packages stay "probably". It is not monitoring: it runs only when apt installs, and only records.
- **The public share folder (John, 2026-11-19; the names are built, the check is not).** Services that share a folder with others (gnome-user-share's WebDAV and Bluetooth, Samba usershares, and the like) usually share the one `XDG_PUBLICSHARE_DIR` names, `~/Public` in English, and they do not belong on this kind of machine. Its name is a problem: xdg-user-dirs names it in the language of the first login, and when the language changes later the user may keep the old name, so a home folder can hold `Offentlig`, `Public` or a name a translation used years ago (Swedish `Delat` until 2007). So the names it can have come from two places: what the project knows, a table of every name xdg-user-dirs has given it in every language through the whole history of its translations (`src/backend/xdg-public-names.c`, 93 entries, each with the date it came and whether the translation still uses it; generated by `tools/xdg-public-names.py` from a full clone of freedesktop's xdg-user-dirs, so it is tracked in git and made again when translations change; `tests/test_xdg_names.c` holds every name a plain folder name), and what the machine says, inferred at run time: the catalogs installed (`xdg-user-dirs.mo` in `/usr/share/locale/*/LC_MESSAGES/`, and on Ubuntu in `/usr/share/locale-langpack/`, since Ubuntu strips the package's own and ships them with the language packs only: 7 on John's machine, 2026-11-19, matching freedesktop's), read directly with a strict `.mo` reader, never by switching the locale, plus `~/.config/user-dirs.dirs` and `user-dirs.locale`. A name alone proves nothing (a folder can be made by hand), so what is said of it is *probably*. **Its task (John, 2026-11-19): find duplicates, and say that they can make it unclear what may be published openly on the local network.** A desktop that follows XDG has one standard place for this (it does not mean the user keeps files there): first find that place, then other folders in the home folder with a name it could have had, which can make it unclear which one the user actually uses, and say so. It is a plugin of its own: finding what may lie open, perhaps not by the user's own choice, is part of the first scan (Home, as the user, no password), while asking the user whether they mean to use that place is one of the plugin's parameters, on its page 1 (John, 2026-11-19). The finding is built (`src/backend/public-share.{h,c}`, `gaudit_public_share_find`): `XDG_PUBLICSHARE_DIR` from `~/.config/user-dirs.dirs`, read strictly in the form xdg-user-dirs writes (`"$HOME/…"` or an absolute path, backslash escapes; any other variable, a command, text after the closing quote or `..` is *unknown*, never a guess; the home folder itself means switched off; the last definition counts); the system's default from `/etc/xdg/user-dirs.defaults`; the language from `user-dirs.locale`; the names from the table, every installed catalog, the system's default and the standard folder's own name; then every folder or link straight in the home folder with one of them (exact, or ASCII case ignored and said so; a link with where it leads, never followed), each with the language its name belongs to (the one in `user-dirs.locale` first), whether a catalog on the machine gave it, whether a translation still uses it, and whether it is the standard one. A folder on another filesystem than the home folder (a mount: another disk, a network or cloud folder such as an rclone mount) is never listed, since listing it may fetch it over the network: it is marked and said to be not looked in, and the tidying refuses it in the page, the orchestrator and the backend (John, 2026-11-19). The `.mo` reader takes both byte orders, checks every offset against the file, at most 1 MiB, and trusts none of a catalog that is not well formed. **Its fixes tidy the structure, nothing else (John, 2026-11-19).** A duplicate made by a change of language (on John's machine `Offentlig` and `Public`, both empty) is merged into the folder in use. First it is checked, changing nothing, whether everything can be moved (`gaudit_public_merge_check`, John 2026-11-19): a name already in the folder in use is a clash, for the user to decide (rename one, or keep both apart), and an entry on another filesystem is never copied; the page shows this before anything is pressed. Only when nothing stands in the way is anything moved, each entry as it is, so a merge is never left half done; each move is still `renameat2(RENAME_NOREPLACE)`, so nothing already there is ever replaced should something appear between the check and the move. Then the duplicate is removed, but only when it is empty (`unlinkat(AT_REMOVEDIR)`, which refuses anything else by itself). Files are never deleted: a user who wants that is told to do it themselves. Both run as the user, on folders straight in the home folder by one plain name, the user's own, opened beneath the home folder without following any link (`gaudit_public_merge`, `gaudit_public_remove_empty`). Which folder is in use comes from `user-dirs.dirs`, or the user's answer among the parameters; when the user says the other one is meant, the fix is to point `XDG_PUBLICSHARE_DIR` there instead. The page is a sequence dialog: what would be moved, the button, the result, then removing the empty folder. **Services that share the folders come first (John, 2026-11-19).** Before anything is moved or removed, the program finds out whether a service shares one of these folders, since moving the contents away from a folder Samba shares would change what is shared without the user noticing; while one does, the fix moves nothing and names it. Such services are asked about too, among the parameters: the user may have chosen them on purpose, but most often does not know they run. Found as the user, from files and `/proc` only, never by asking the tools, each in a fixed table like the vendor table: Samba (`/var/lib/samba/usershares/*` and `/etc/samba/smb.conf`, `path=`), which is also what the file managers' one-click sharing makes (nautilus-share in GNOME Files, Dolphin in KDE), so those are seen wherever they point, and are shown even when they point elsewhere, since they share on the local network just as the public folder does; GNOME Sharing (gnome-user-share's WebDAV and Bluetooth, which always share `XDG_PUBLICSHARE_DIR`); DLNA/UPnP media servers (Rygel's `uris=`, MiniDLNA's `media_dir=`); and other HTTP/WebDAV/FTP/SFTP services, from the listening ports joined to the user's own processes. Services running as root or another account are seen running, often not what they point to, and the page says so. File-sharing programs (qBittorrent, Transmission, Deluge, KTorrent and the like) share from wherever they are told, in their own formats: the program says they are installed or running, that they can share files from any folder, and that it cannot see which; it does not try to read their lists (John, 2026-11-19). That is said as what they do, never as a level of danger. **The tidying is the point; what programs do is hard to trace (John, 2026-11-19).** The plugin tidies known folders, from what historical changes can have left (names changed with the language); deviations made by running programs are hard to trace, so it does not try to map them beyond the check above, which only keeps a merge from moving what a service shares. Giving shared folders (Samba usershares) the public folder's icon was considered and set aside for now: in GNOME Files it would be a metadata value, but in Dolphin a `.directory` file inside the shared folder, which those connecting would see, and an icon left after a share is switched off would say something untrue. Where usershares live is read from `usershare path` in `smb.conf` (default `/var/lib/samba/usershares`). **The good practice behind it (John, 2026-11-19).** What gAudit is establishing is a good practice, given as recommendations, not warnings, since a setup may be chosen on purpose: what is shared on the local network is gathered in one place, the public share folder, because sharing scattered folders makes it unclear what is open, however common it is; and cloud services each get a folder of their own under one gathering folder, `~/Cloud` (named in the user's language, see *Names in the user's language* below), e.g. `~/Cloud/Dropbox`, `~/Cloud/Nextcloud`, so there is one place to see what is synchronised out of the computer. The gathering folder has the same problem of names as the public folder but no standard to look them up in, so its names are kept by hand in the table, with where each was seen. **Cloud folders are shown and recommended on, never tidied (John, 2026-11-19).** Such folders are often put straight in the home folder; a gathering folder is better. But merging them, or moving them, is never done by the program: a cloud folder mirrors an account somewhere else, so moving a file out of it deletes it there and on every computer that syncs it, moving one into another service's folder uploads it to another provider, and moving a service's folder behind its program's back makes the program think it is gone (it may sync everything again, or take it as deleted). So the cloud plugin, a plugin of its own, shows which cloud folders there are, which program each belongs to, and whether they are gathered or scattered, and recommends gathering them, through each program's own setting for where its folder is, never in the file manager; its page explains why and points to that setting, and moves nothing. Duplicates of the gathering folder (`Cloud` and `Skytjenester`, say) are treated the same, since they hold services' folders. **What the cloud plugin looks for (John, 2026-11-19).** It only finds out whether known services are there (installed, or a folder of theirs); keeping them up is the business of their own programs. File storage only (Dropbox, OneDrive, Google Drive, Nextcloud, Proton Drive, Tresorit, pCloud, MEGA and the like), never object storage (S3, B2) or general tools such as rclone. The largest services and those with generally good security, in a short table kept by hand, each with three properties and where and when each was checked: end-to-end encrypted or zero-knowledge (always, optional, no), the jurisdiction the provider is under, and whether the client is open source. What is recommended: zero-knowledge, a jurisdiction with strong privacy, open source, so the security can be shown, and upkeep (John, 2026-11-19): the client kept up to date by the system, as a package from the distribution, from the vendor's own software source, or as a Flatpak or snap. An AppImage, or an install updated by hand, falls short: it is troublesome to keep up to date, and a client that syncs files out of the computer is a poor place to miss security fixes, as Updates says of software outside any package manager. So the table has a fourth property, how each client is updated (pCloud ships only an AppImage; how the others ship, apt sources of their own for Dropbox, MEGAsync, Insync and Jottacloud, Tresorit's own installer script, Nextcloud and `onedrive` in the distribution or as Flatpaks, is to be checked when the table is built), and an AppImage is never recommended. A service that falls short is said to, briefly and kindly, without dwelling on it; "the provider can read your files" is the same kind of fact as who else can read a file. Only verifiable, documented properties are said: never lawsuits or reputation (MEGA's are mostly about its predecessor and founder), since they say nothing of who can read the files today, go stale, and read as a judgement of a company; where the law does decide who can get at the files, the jurisdiction says it. Flaws bound to a version (MEGA's cryptographic ones, found by researchers and fixed) belong in the table's sources, not in what the user reads. - **A plugin owns its profiles.** In the UI a plugin is a folder and its profiles are the entries in it (as in Secrets). Choices in the plugin's interface, and the data it imports, may limit which profiles are offered.
- **Roles.** The plugin is a signed package of data and programs, never code in gAudit's processes: a description, a collector that gathers data from the machine (started by the helper with the privileges it declares), Guile profiles that hold its logic (data in, structured decision out; see *Acting on the system*), templates and a fixed vocabulary. The helper is gAudit's own and shared by all plugins: it starts collectors, checks decisions against the vocabulary and writes files from the plugin's templates with its few built-in formatters.
- **A run goes collectors → exports → Guile.** Exports are taken from collector output before any rule has seen it, so no rule, not even the exporting plugin's own, can change what is exported. Decisions are never exported: data flows from the machine into rules, never from one plugin's rules into another's.
- **Data is private unless exported, and seen only if imported.** A plugin declares what it exports (under its own namespace only, e.g. `core.packages.installed`) and what it imports. Imports arrive as one subtree per exporting plugin, `(imports (core.packages …) (org.example.foo …))`; the subtrees are independent and immutable, and the importer decides what to use. The exporter decides what leaves it (e.g. private-file findings never with paths). An import from a plugin that is missing or not authorized makes the profile unavailable, never empty data that looks like "nothing found".
- **Script kinds.** A plugin's Guile scripts are of three kinds: *reports* (data in, findings out), *fixes* (a detected finding in, an action out) and *configurations* (data and any answers in, a structured decision out). A fix may point to a configuration, so the finding usually picks the configuration for the user; browsing configurations directly is the exception.
- **Surface and deep reports.** A plugin may have a surface report and a deep one. If it has a surface report, that report runs as part of Home. The deep report runs on request, from the plugin's page, and its result comes back to the plugin's Home row. Depth and privilege are separate axes, declared separately: depth decides where a report belongs (Home or on request), privilege only whether a password is needed. Surface without password: Home's probes. Surface with password: Home's *Checks that need your password* (the firewall). Deep without password: the secret scan of the home directory. Deep with password: package integrity.
- **Report levels.** Each report states its level, set by the plugin: *Quick*, *Normal*, *Thorough* and, if needed, *Extra thorough* (nb *Rask*, *Vanlig*, *Grundig*, *Ekstra grundig*) for Home, and *Full* for the plugin's own page. The user sets one level, for Home only (the rest of the app, the plugins' own pages, always runs at *Full*; tentative), and Home lists every report at or below it; gAudit never judges how important a single plugin is. No level is named so that choosing it sounds unreasonable (e.g. *Paranoid*). The level also sets how much is shown: at the lower levels warnings only, at the highest also information otherwise held back on purpose (e.g. classic snaps, listening ports). Levels are cumulative: a *Thorough* report shows everything a *Normal* one does, and a *Normal* one everything a *Quick* one does, so going up a level never makes rows disappear. Reports below *Full* take no parameters, since their collection needs none. The level is kept in dconf, which malware on the account can write, so Home always shows the level it runs at. The plugin format must state what each level promises about time, since a plugin could mark a heavy report as *Quick*; Home's deadline stops it regardless. The level a report is shown at falls back to the next simpler one the plugin has (see *Planned* under *User interface*). The default level is *Quick*, so the first password dialog follows the user's own choice of a higher level, and the user can see that the choice is what brought it up. A *Quick* report should as a rule not need administrator rights, but it may (some quick reports will need them); at the default level it then shows as a row saying it needs administrator rights, since the password is never asked for when the app opens.
- **Recommendations (John, 2026-11-15; implemented).** A report row may be `(verdict advice)`: a recommendation, not a finding, for something that may be off for a reason (e.g. automatic installation of updates). It has its own symbol on page 2 (information, accent colour, "Recommendation"), counts as fine, so it never makes the verdict worse, and never reaches Home, so gAudit does not nag. Its fix page explains, and says to keep it as it is when it is so on purpose.
- **Home condenses what fails (John, 2026-11-15; implemented).** A plugin's report page shows everything; Home shows only a condensate of what fails. Each row in the plugin's group on Home is a summary ("37 security updates are waiting", "3 secrets can be read by every account"), never one row per item and never a row for what is right; when nothing fails, one row says so. Home is mostly a filtered and summed selection of page 2: page 2 is split further, since its rows carry the chevrons to the fixes, while Home sums them up (Private Files: one row per kind of reach; Updates: the three groups of packages without a source as one). The rule script gives these rows as `(home (verdict V) (title MSG) (subtitle MSG))` elements, which page 2 ignores; a rule that gives none gets one row from the report's verdict and title. The group's description says when it was checked ("Checked at 14:32"). Rows that are unknown or not supported are shown, since they are not right either.
- **Updates follows the Private Files pattern (implemented, 2026-11-15).** `core.updates` is a collection plugin: `gaudit-orchestrator updates quick` writes facts only, one `(fact (key K) (status S) (value N) (text "..."))` line per key from a fixed list, then `(facts (count N))` (`src/plugins/updates/common/updates.h`; status 0 known, 1 unknown, 2 not supported, 3 does not apply), read through the backend, never through an admin tool. Its rule `rules/report.scm` decides everything. Page 2 is grouped by the questions a reader asks, not by apt's steps (John, 2026-11-15: "looking for" and "installing" ran together): *Status now* (security and other updates waiting; when updates were last looked for is the subtitle of that status, and a row of its own only when too old or unknown), *Keeps itself up to date* (looking for updates, the daily jobs, installing by itself), *Where updates come from* (the security source, packages without a source, package systems), *Package files*. The judgements, each with its own fix: *Looking for updates* (never: warning; the daily job off: warning; not looked for in 7 days: warning), *Installing updates* (pending security updates: always a warning; other pending updates: a warning when nothing installs them automatically and no package has been installed or updated for more than two weeks (`last-change`, from `/var/lib/dpkg/status`), information otherwise; the install job off while set up: warning; automatic installation off: a recommendation, John, 2026-11-15), *Where security updates come from* (a mirror: warning), *Software no source keeps up to date* (the three groups), *Package systems* (the expected one missing, others with packages). A check a backend cannot do shows "Not supported on this system yet", never hidden. Home shows one row per problem in that order, each a summary (the packages without a source as one), or one row when nothing fails. Its text domain is `gaudit-updates`. On Debian and Ubuntu the fix pages run their commands from `common/apt-ops.h` (see *Running a system tool from a fix page*): *Install the Updates* is `apt-get … upgrade --update` with apt 2.7.0 or newer (fact `upgrade-updates`), otherwise two steps, `apt-get update` then `apt-get … upgrade`; *Look for Updates* `apt-get update`; *Switch On the Daily Jobs* `systemctl enable --now` on both timers; the package files' page `apt-get … install --reinstall` with the plain names of installed packages. Each step has its command field with copy and run, and what each part does in plain words; after a step that succeeded, the collection runs again at the same depth. Other backends' pages give their fixed command to copy only (never `pacman -Sy` alone). The packages without a source lead to their list. The seven update probe rows are gone from Home's status. Package integrity is Updates' *Thorough* level and part of its full report (implemented, 2026-11-15): the command `user updates quick then run integrity` is a *compound run*, the facts as the user, then the check in the helper (the password), whose `(integrity-file ...)` and `(integrity ...)` lines join the same collection, each checked by the plugin's line check; a run as the user can never give those lines itself. Whether a run needs the password is decided by its command (`gaudit_command_needs_admin`: `run ...` or `... then run ...`), not by the task, so a plugin's levels may differ. The helper part is Debian's only (`helper_backend`: dpkg's md5sums); elsewhere the commands run without it. The report's *Package files* section has one summary row and a row per file listed, all leading to the same fix page (`sudo apt install --reinstall` with the plain package names from the cached lines).
- **Home's groups from today's probes (implemented; the Updates plugin is `core.updates`).** The core probes become core plugins, each a group on Home, Private Files first (John, 2026-11-15: its findings are of immediate use and easy to fix, so the user sees at once what gAudit is good for), in the sidebar too: *Updates* (nb *Oppdateringer*, the word people use; also the plugin's name in the sidebar, whose full report covers updates and package integrity) (package system, other package systems, when updates were last checked for, pending updates, automatic updates, source of security updates, packages without a source; package integrity is its *Thorough* report, not a plugin of its own), *Flatpak* and *Snap* (only when installed), *Firewall* (whether one is installed, services listening on ports, which the firewall check turns into a finding, and the check with the password at *Normal*), *Antivirus* and *Private Files* (no probe rows: its Home row is its own report at every level, John, 2026-11-14). Network is more than ports (e.g. DNS, Wi-Fi, VPN); that would be a plugin of its own later, while listening ports stay with the firewall.
- **The collection is the same; only the presentation differs (John, 2026-11-14).** What Home shows for a plugin comes from the same collection code as the plugin's page 2, so Home is always identical to page 2 or a subset of it. A finding on Home that page 2 does not list is a bug, never a difference in levels: a deeper level adds to the same collection, it does not replace it with another.
- **Collections are cached, reports are made from them (implemented, `src/gui/gaudit-report-run.c`).** A plugin whose run is a collection (run command `user <mode>`; its `collection_line` checks each line strictly, and says which is the last) keeps its latest collection in the GUI's memory for the session, never in a file. The report is made from it by the rule script through `gaudit-orchestrator report <plugin-id>`, which runs `gaudit-engine` with a fixed path and an empty environment and passes at most 60 KiB on; the GUI parses the lines strictly (`src/gui/gaudit-report.c`) and shows them generically: the verdict as the shield, then a group per section and rows with their verdict symbols. Formatting is assumed fast; collecting is what is cached. Home's rows and page 2 come from the same collection: the rows are the report's `(home ...)` elements. Rows have no chevron of their own. *Run* on the plugin's page always collects anew. A fix a row names (`(fix ID (item N))`) is built by the plugin's `fix_page` from collection line N, never from report text.
- **A plugin localises its own report.** Its texts are msgids in its own text domain (`gaudit-private-files`), with `{key}` placeholders the GUI fills in (never printf formats). The plugin's `po/` holds `POTFILES.in` (its C code, keyword `P_`), `RULES.in` (its rule files, Scheme, `G_` and the plural pair `N_`), `LINGUAS` and `<lang>.po`; `gaudit_plugin_domain` in `cmake/I18n.cmake` extracts both into one `.pot` and builds the `.mo` files into the same compiled-in locale directory. The plugin's description (title, summary, details) stays in gAudit's own domain until the description format exists.
- **Collection levels.** A collector can gather data at more than one level of depth, and each report states the level it needs. Home's reports use a simplified collection, so Home shows quickly; a full report on the plugin's page may ask for a new, full collection. A deeper collection can serve a report that needs less, never the other way round.
- **One collection, many scripts.** A plugin's collector runs once per level, and its data (with the imports, frozen at the same moment) is the basis for all its scripts until a new collection is asked for explicitly, so every script sees the same picture of the machine. The collected data steers what the helper writes as root, so it is held in memory for the session (or root-owned), never as a file in the user's area.
- **Guile sees a copy.** The engine is its own process and gets the data over a pipe; each profile is evaluated in a fresh playpen, so nothing survives from one evaluation to the next.
- **Distribution and backend are core exports**, never taken from another plugin, so no third-party plugin can hide or unlock others' profiles by lying about the system.
- **Templates belong to the plugin, formatters to the helper.** A template is fixed text with typed slots, signed with the plugin. The helper has one formatter per file format (ufw, nftables, systemd unit, ini, …) and fills slots only with vocabulary values, escaped for that format. A new configuration in a known format needs only a new template; a new file format needs C code.
- **Actions.** A decision may set up an action (a button) on the plugin's own page that fixes a concrete problem. Its label and summary come from fixed message ids, never from text the plugin supplies; the route from Home to the plugin stays gAudit's own.
- **No monitoring.** This lets gAudit check the system and change configuration on request, nothing more: no continuous monitoring, and no tuning in a tight loop. What it sets up (e.g. a timer) is run by the tool itself.
- Still open: whether the whole model can be presented so an ordinary user understands it.

### Private Files is the pattern (John, 2026-11-15)

Private Files is the minimum implementation of a plugin; the others are variations on it, with the same trade-offs and methods. A new plugin, or one moved over (Updates, Firewall, …), follows this unless a concrete reason says otherwise:

- **Its folder** `src/plugins/<name>/`: `plugin.c` (description), `common/` (the collection's line format, parsed strictly), `orchestrator/` (the collection as a mode of `gaudit-orchestrator`, run as the user unless it truly needs the helper), `rules/report.scm` (the report), `po/` (its own text domain), the GUI part (line check and fix pages).
- **One collection, several depths:** a command per Home level (`home_commands`, the nearest at or below the chosen level is used), and the full collection with the parameters (`run_command`). A deeper collection holds everything a shallower one does; Home is always identical to page 2 or a subset of it.
- **The rule script decides the report:** verdict, sections, rows, notes, from data only; texts are msgids with `{key}` placeholders in the plugin's domain; a fix names a collection item, never a command. Thresholds and judgements live in the rule, counting in the collection.
- **Cached for the session, in memory:** Home shows a condensate (one row per problem, see below); the chevron is always there and lands on the report from the cached collection, or on the run under way; reports for Home are simplified, the one after *Run* on *Parameters* is the report.
- **Parameters only for the full run**, kept in the plugin's relocatable settings, read back checked, passed as arguments the orchestrator checks again; the report names what it covered (folders, limits).
- **Page 2 is a report;** each row's verdict a symbol; a row with a problem leads to its fix page, built by the plugin from the cached line.
- **Long runs** report progress (and roughly where), ask whether to go on instead of a hard limit, can be stopped, and name what was slow, large or cut short; limits are honest (said in the report) rather than hidden.
- **Tests:** the line format round-trips and refuses what it should; the collection is checked on a tree built by the test (never the real home), including that the shallow level is a subset of the deep one; the rule runs on fixed input in the engine test.

### Trust: list of trusted owners

- We publish a **signed list of trusted owners**, signed with the core key. It has the same protection as the manifest: increasing version number, expiry date and rejection of older versions.
- Each entry holds the owner's name, repo URL, public key(s) and namespace.
- Owners sign their own plugins. The repo URL in the plugin's signed description must match the list.
- **We do not audit plugins.** The list only says who the owner is, not that the code has been reviewed.
- **Origin is always shown.** The UI shows repo and owner for every plugin and every finding, and states clearly that the plugin has not been reviewed by gAudit.
- **Revocation.** When an owner is removed from the list, their plugins are no longer loaded, and the user gets a clear explanation.
- We expect few owners, so the list is maintained by hand.

## Threat model

We program defensively and assume an infected machine may try to produce misleading results or hide programs.

- **We protect against:** a compromised user account, common malware, and manipulation from the user's area, for example `.desktop` overrides in `~/.local/share/applications/`, environment variables (`LD_PRELOAD`, `LD_LIBRARY_PATH`, `GTK_MODULES`, `GIO_EXTRA_MODULES`, `GUILE_LOAD_PATH`) and modified rule files.
- **We try to detect, but promise nothing about:** a compromised root. We look for inconsistencies and deviations from packages, and on suspicion recommend a check from bootable USB.
- **Out of scope:** well-hidden kernel rootkits and firmware attacks.
- **Defence in depth.** A layer that only makes an attack harder is still worth having, even when it cannot stop it, as long as it is described for what it is and never relied on as the only defence (e.g. the copy button's check of the shown command).
- A green result means "no signs found", not "the machine is clean". The UI and documentation must say so honestly.
- **No threat levels (John, 2026-11-15).** gAudit says who can reach what, never how likely an attack is: judging likelihood takes knowledge of the machine and its users that ordinary users cannot give and gAudit cannot assume, and it gets too diffuse for them. No warning is softened by how the machine is used ("only I use it"). General recommendations, and later a summary of the most important findings, are possible. gAudit never recommends deleting anything, backups or single files: it recommends tightening the access to them. The one exception is an empty folder left from tidying a structure (the public share folder's duplicates, John 2026-11-19): it holds nothing, and removing it can only succeed while it is empty.

### Known gaps to close before an outside review (John, 2026-11-16)

Every known security gap is to be closed before security people are asked to look at gAudit, once it is more complete. Found so far (a review of the code by hand, 2026-11-16), in the order they are to be done:

1. **Untrusted data parsed as uid 0 in `vendor-verify` (closed, 2026-11-16).** The plan was to parse as `nobody`, but the part that parses is the part that decides: a verifier taken over by a crafted signature can simply answer "good", and root then installs the package anyway, so a split only moves the problem. What was done instead: the signature is checked with `sqv` (Rust, so parsing a hostile signature is far less exposed to memory errors) in place of `gpgv`, and gAudit's own parser of the signature file is gone; only the text `sqv` authenticated is read. The remaining exposure is the ar parser (a few lines of C over fixed-size headers) and `dpkg-deb --field`, which only ever sees a package whose parts already matched the signed list.
2. **The rule engine's descriptors and signals (closed, 2026-11-16).** Signals only to itself, inherited descriptors closed, stdin at `/dev/null` once read; `gaudit-engine selftest` shows each denied. stdout stays open by necessity (see *Rule engine: Guile*).
3. **The GUI's own environment (closed, 2026-11-16).** At the very start of `main`, before GTK is loaded, `gaudit_environ_clean` (`src/gui/gaudit-environ.c`) looks for variables that make the GUI load code or modules from a place of the caller's choosing (every `LD_*`, `GTK_MODULES`, `GTK_PATH`, `GTK_DEBUG` for the inspector, `GIO_EXTRA_MODULES`, `GIO_MODULE_DIR`, GDK Pixbuf's, GStreamer's, `GSETTINGS_BACKEND`, `GSETTINGS_SCHEMA_DIR`, `GI_TYPELIB_PATH`, `GCONV_PATH`); with any set, gAudit starts itself again (`/proc/self/exe`, the same arguments) without them, and *This computer* on Home gets a warning row naming them, which says plainly that code they pointed to may have run all the same (an `LD_PRELOAD` library runs before `main`), so it is a sign to look into, not proof of a clean process. `GTK_IM_MODULE` stays: it picks among installed input methods, needed to type Chinese or Japanese. The names travel to the new start in `GAUDIT_REMOVED_ENV`, and each variable with its value (cut at 4 KiB, at most 32) in `GAUDIT_REMOVED_<n>`, never passed further; ones the caller set itself are dropped before the new start, and setting them by hand where nothing is removed only shows a false warning. **The row leads to a page, judged by the values (John, 2026-11-17):** *Settings That Load Code* lists each variable, what it does, and every folder or file it names, judged from `/` down, as written and where links lead (`gaudit_environ_judge_path`): only root's and written only by root is fine; another account's, writable by every account, an empty or relative entry (the folder the program is started in), or writable by a group is a finding. A group counts unless it is root's (gid 0) or has no members, as its own or anyone's primary group, since only root can then add one; the page names the group and its members (Debian's `staff` for `/usr/local` is such a case). A module named without a folder (`GTK_MODULES=gail:atk-bridge`, set by the desktop session on Ubuntu) is judged by the file GTK 3 would load it from (`lib<name>.so` or `<name>.so` in `…/gtk-3.0/{3.0.0/<host>/,3.0.0/,<host>/,}modules` under the multiarch, `lib64` and `lib` folders; `gaudit_environ_module_file`), and with no such file nothing is loaded; the page says the program itself uses GTK 4, which ignores the variable, while every GTK 3 program the user starts reads it (John, 2026-11-17). The `grep` also covers `~/.xsessionrc`, `/etc/environment.d/`, `/usr/lib/environment.d/` and `/etc/X11/Xsession.d/`, where the system sets such variables for every account, and variables that load no code (`LD_DEBUG`) are listed as such. When everything points only to the administrator's folders (CUDA's `LD_LIBRARY_PATH=/usr/local/cuda/lib64`), the row is a recommendation, not a warning. The page says where such settings are usually made (started from a terminal the program gets its settings, from the menu only the login's), gives a copyable `grep` for the lines that set them (only plain names go into it), and what to do: point them only to the administrator's folders if the user set them, and otherwise find out where they came from before changing anything. An empty entry (a colon first, last or twice, as in CUDA's `LD_LIBRARY_PATH=/usr/local/cuda/lib64:` from `…:$LD_LIBRARY_PATH` on an empty variable) has its own text: programs then look in the folder they are started from, which is the user's. How to write it right in each kind of file is the shells' business, not the program's (the scope rule), so a row with the link icon (`gaudit-external-link-symbolic`) opens the wiki's *This Computer* page in the browser on a click, a fixed address under `GAUDIT_WEBSITE`; the program never reads the user's shell files (John, 2026-11-17). `tests/test_environ.c` starts itself again the same way.
4. **Developer builds run the helper from the build tree (closed, 2026-11-16).** Outside developer builds, configuring refuses (`FATAL_ERROR` in `CMakeLists.txt`) when any compiled-in path (helper, orchestrator, engine, collectors, rules, vendor keys, locale, schema, libexec) lies inside the build or the source tree, so such a build cannot be made by mistake; the `release` preset gives installed paths only (`/usr/local/libexec/gaudit/gaudit-helper` and so on). The test `release-paths` configures a non-developer build with its prefix inside the build tree and expects the refusal.
5. **The orchestrator's seccomp filter (closed, except the session, 2026-11-16).** Every mode but `session` sets `no_new_privs` and the shared deny list (`gaudit_sandbox_restrict_net`), which what it starts inherits: no network sockets in any mode but `updates latest` and `updates download`, which start `wget` or `curl`, and `cloud plain` and `cloud names`, which start `rclone` (on a click only, John 2026-11-19) (raw packet sockets never); local sockets stay, for snapd. `tests/test_sandbox_net.c` holds each case. Left open on purpose: the `session` mode starts `pkexec`, which is setuid, and `no_new_privs` would keep it from ever becoming root; it parses only the helper's lines and the GUI's commands, strictly.
6. **The signed manifest, the helper's checks of gAudit itself, the root-owned log** (helper's side built 2026-11-16, shown on Home 2026-11-17; gAudit's first key made 2026-11-17, `data/keys/manifest/gaudit-manifest.pub`, id `8A40C6D70584B480`; see *Signed manifest*): still to do, signing a real release with that key, and the rule files read through the manifest once they can come from anywhere but the package.

Fixed in the same review: the download path no longer falls back to `O_NOFOLLOW` without `openat2` (it followed links on the way, as root); a download with `wget` is stopped as soon as the file passes 1 GiB, not checked only afterwards.

Accepted: whether the program that keeps a package up to date is installed (ClamUI) may be read from the user's own Flatpak folder, so malware on the account can make a package left behind look kept up to date. It only hides a recommendation, and a Flatpak installed for the user alone is ordinary.

## Process and privilege model

```text
GUI (user)  ──>  orchestrator (user)
                   ├─ privileged helper (pkexec, C, minimal)
                   │     └─ fork → check processes (C, privileges dropped per check)
                   │            └─ write S-expressions to a pipe
                   └─ rule engine (Guile, playpen, no privileges)
                          └─ data in → verdict + explanation out
```

- The GUI always runs as the ordinary user and contains no security logic. It only shows finished verdicts.
- Privileged operations are done by a small, separate helper started via **polkit/pkexec**, never setuid. The polkit action uses `auth_admin`, never `_keep`: polkit itself remembers nothing, because its memory would let anything on the account start the helper without a password, unseen by the red disc.
- **Elevated rights are leased (implemented, `src/helper/lease.c`).** In its session mode the helper stays alive after a run and accepts further commands, one per line from the orchestrator, without a new password. The rights end 2 minutes after the last run finished (each run within that time renews it, any number of times), and never later than 30 minutes after the password was given; a run under way when the cap is reached may finish, then the rights end. The helper enforces this itself on `CLOCK_BOOTTIME` (time asleep counts), since everything on the user's side could be made to stretch it. An unknown command, or the end of its input, ends the session too.
- The helper (`src/helper/`) runs only as root (pkexec, or root directly in containers), accepts only known commands, reads `PKEXEC_UID` for reporting only, then clears its environment, sets umask 077, changes to `/` and closes every inherited descriptor above 2. Each check runs in a forked child that is sandboxed before any check code runs (`sandbox.c`); the only exception is the fixed system-tool operations of *Running a system tool from a fix page* (`unconfined`: root as with sudo, the environment cleared to `PATH`, `DEBIAN_FRONTEND=noninteractive`, `LC_ALL` and `HOME`, started with `execve` and a fixed argv, never a shell), writes to a pipe with a 4 KiB limit and a 10 s timeout. `gaudit-helper selftest` reports the privileges the children actually end up with, so the sandbox can be verified. The helper writes `(helper-start ...)` as its first line, so the caller knows the authorization went through.
- **Runs on request go GUI → orchestrator session → `pkexec` → helper session.** The GUI keeps one `gaudit-orchestrator session` while it has windows and sends it commands on stdin (`run firewall`, `quit`), one helper part at a time (runs as the user have orchestrators of their own). For the first run, or once the lease has ended, the orchestrator starts `/usr/bin/pkexec --disable-internal-agent <helper> session` with `execve`, a fixed argv and an empty environment; a run asked for while the helper is leaving waits for it and starts a new one. Each run has 5 minutes (typing the password included). Once the helper is root it cannot be killed from the user's side, only asked to stop by closing its input; its own checks have a 10 s limit. The orchestrator parses the helper's lines strictly and writes the language-neutral events of `gaudit/run.h` to the GUI: `(elevated (on 1|0))` when the helper starts and ends, and per run the result and `(end (status ok|cancelled|denied|failed))`. pkexec's exit 126 (dialog dismissed) is *cancelled*, 127 (not authorized) *denied*, provided the helper never started. The GUI treats these events like the status lines: strict, size limited, anything out of order ends the session. Closing the last window ends the session and with it the rights.
- In developer builds the helper is run from the build tree, so pkexec asks without the policy's message (the policy is not installed) and runs a binary the developer can write. Never for packaging.
- Each check process does this at startup:
  - `setresuid`/`setresgid` to the least privileged user possible
  - drops capabilities it does not need (libcap)
  - sets `PR_SET_NO_NEW_PRIVS`
  - installs a seccomp filter: a deny list (ptrace, process_vm_*, mount and friends, chroot, kexec, module loading, bpf, perf_event_open, userfaultfd, keyrings, setns/unshare, swap, handle-based open, iopl/ioperm, clock and host name changes) plus no IPv4/IPv6/packet sockets; denied calls fail with EPERM. A deny list rather than an allow list, because checks only read files and /proc, and an allow list would break with new glibc and kernel versions
  - either becomes `nobody` (65534, fixed, no NSS) after emptying the capability bounding set, or stays root with exactly the capabilities it needs (bounding set limited to them, nothing inheritable or ambient)
  - closes inherited file descriptors
  - clears the environment completely
- Programs are started with `execve` and absolute paths, never `system()`/`popen()`, and an inherited `PATH` is never trusted.
- All data from child processes is untrusted input, with a size limit and a strict format.
- Data is read directly from `/proc`, `/sys` and configuration files where possible, instead of parsing output from external tools.
- Independent sources for the same fact are compared, e.g. `/proc` vs `ps`, `/proc/modules` vs `/sys/module`, `/proc/net` vs `ss`. Discrepancies are reported as findings.

## Rule engine: Guile

- Reports are evaluated and explained with Guile (`guile-3.0` from Ubuntu), so evaluation can change without recompiling. Python was rejected because it pulls in too much.
- **Playpen, not sandbox, in descriptions (John, 2026-11-14).** In documentation and anything a person reads, the rule engine's confinement is called a *playpen* (nb *lekegrind*): it keeps a rule in, but nobody claims there are no gaps between the bars. Code and Guile's own module (`ice-9 sandbox`) keep the word sandbox.
- Guile runs in a separate process without privileges and with seccomp. It has no network or file access; rules receive their content over a pipe.
- Rules are evaluated with `ice-9 sandbox` (`eval-in-sandbox`), with a restricted set of bindings and time and memory limits. Rules do no I/O.
- Check data is parsed with `read` on size-limited input. The reader is never extended, and incoming data is never evaluated.
- **Implemented (`src/engine/main.c`, first rule `src/plugins/private-files/rules/report.scm`):** `gaudit-engine report <plugin-id>` reads `(input (system ...) (collection <the collection's lines>))` on stdin (at most 512 KiB, invalid UTF-8 replaced) and writes the report one element per line: `(report (verdict V) (title MSG) (description MSG))`, then `(section ...)`, `(row (verdict V) (title MSG) (subtitle MSG) [(fix ID (item N))])` and `(note MSG)`. MSG is `(msg "text" (key value) ...)`, `(msgn "one" "many" n ...)` or `(text "plain")`: English msgids with `{key}` placeholders, never printf formats, in the plugin's own text domain, so the plugin localises its report. A fix names a collection item by position, never a path: the command is built by gAudit from the collected data, so a rule cannot put text into a command. The rule script decides the whole report and may leave sub-reports out from the data it gets, including the system identification; exports and imports from other plugins come later. The rule file is read from a compiled-in directory only (`<rules dir>/<plugin-id>/report.scm`; the id is a name, never a path) and, outside developer builds, must be root-owned and not writable by others until the signed manifest exists. The environment is cleared before Guile starts (no `GUILE_LOAD_PATH`, no auto-compile), Guile's modules are loaded, then no_new_privs, the shared seccomp deny list and the engine's own filter (`src/engine/confine.c`: no files opened, no changes to the filesystem, no sockets of any kind, so neither D-Bus nor the network, no `execve`, no new process; threads stay possible for Guile's collector) go on before the rule runs (John, 2026-11-14: a rule must never read or write files, talk on D-Bus, reach the network or start processes; Guile has no bindings for any of it, and the process cannot either). `gaudit-engine selftest` tries each of these once confined and reports what was denied. This is defence in depth: it makes an attack harder, it promises nothing. Signals go to the engine itself only (`kill`, `tgkill`, `rt_sigqueueinfo` and `rt_tgsigqueueinfo` to its own pid; `tkill` and `pidfd_send_signal` not at all), so a rule that got out cannot stop the orchestrator or the GUI, also not through `kill(0, ...)` to the process group; Guile's collector signals its own threads and its time limit itself, which stays allowed. Every descriptor above 2 is closed at start, and stdin points at `/dev/null` once the input is read (John, 2026-11-16). Known gap: stdout stays open, since the report goes out through it, so a rule that got out could write there; the orchestrator and the GUI parse it strictly and with a size limit. The signed manifest is what keeps a bad rule from being loaded at all. The rule runs with `all-pure-bindings`, a 2 s time limit and a 100 MB allocation limit. Why a rule failed goes to stderr. `tests/test_engine.sh` checks the report on fixed input, and that rules which loop, allocate without end, open files, call `eval` or do not parse give no report, each for its own reason.

## Signed manifest

- All Guile files and our own code (helper, orchestrator, GUI) have a digest in a manifest that is re-signed on every repo update. The manifest and files may live in the user's area, because the signature provides integrity.
- **The privileged helper verifies:**
  - The public key is built in or installed root-owned from the package (`/usr/share/gaudit/keys/`), never from the user's area.
  - The manifest has an increasing version number. A version lower than the last seen or the built-in minimum is rejected.
  - The manifest has an expiry date (like `Valid-Until`). An expired manifest is reported.
  - The manifest carries the time it was signed, covered by the signature (John, 2026-11-14), so an old signed manifest cannot be passed off as new. Until the manifest exists, rule files are only loaded from the package's fixed, root-owned directory, and from the source tree in developer builds.
  - Each line binds path, size and digest. Only files listed in the manifest are loaded. Extra files are reported, and missing files are a finding.
  - Each file is read into memory once, and the digest is checked on the same bytes that are passed on. It is never reopened after verification.
  - If files or the manifest are missing, the app falls back to the rules shipped with the package and says so clearly.
- Signing: Ed25519 via libsodium. No GPG. The signing key is kept offline, and we need a key rotation plan, e.g. accepting two keys during a transition period.
- **Format and digest (John, 2026-11-16; the helper's side implemented).** The manifest is gAudit's own strict text format (`src/helper/manifest.h`): `gaudit-manifest 1`, then `version`, `signed` and `expires` (seconds since 1970), then one `file <sha256> <size> <absolute path>` per file; SHA-256, since the helper has it already and anyone can check a line with `sha256sum`. The signature beside it (`manifest.minisig`) is minisign's format, Ed25519 checked with libsodium, both the prehashed form minisign makes today (`ED`, BLAKE2b-512) and the legacy one (`Ed`), and its trusted comment; so a release is signed with the `minisign` tool and the offline key, and no signing tool of our own is kept. Checked against minisign's own output. The public keys are built into the helper from every `data/keys/manifest/*.pub` (two during a change of keys; none yet, then the check says the build has no key). The highest version seen is kept root-owned in `/var/lib/gaudit/manifest-version`; lower than it, or than the built-in `GAUDIT_MANIFEST_MIN_VERSION`, is refused, as is a manifest signed more than ten minutes in the future or expired. `tools/make-manifest.sh <destdir> <prefix> <version> <days> <secret key>` makes and signs it for an install tree: the GUI, everything in `libexec/gaudit` and `share/gaudit`, and gAudit's translations.
- **The helper's self-check (implemented, 2026-11-16; on Home 2026-11-17).** `self-check` (`src/helper/selfcheck.c`), root with only `CAP_SYS_PTRACE` and `CAP_DAC_READ_SEARCH` in the sandbox: the manifest as above, every file it lists by size and digest (opened without following a link), every file in gAudit's own folders it does not list (rules, vendor keys, libexec), and the processes that asked: the orchestrator (the helper's parent; pkexec runs the helper in its place) and the GUI above it, each running the program it should (compared with where the expected path really leads, since the kernel names the real file), with no variable that loads other code (the GUI's own list, `gaudit-environ.c`), and no executable code from outside `/usr/` and `/lib*` or not root's. It writes `(self-file ...)` and `(self-process ...)` lines (at most 40 of each) and `(self ...)` with the counts and how many it listed, the run events of `gaudit/run.h`, so the orchestrator (`run self-check`) and the GUI read them with the same strict parser and check the counts match. **Shown as a row of *This computer* on Home, *The program's self-check* (nb *Programmets egenkontroll*; John, 2026-11-17):** at *Thorough* and above (and once it has a result), run last in the level's queue since it needs the password, waiting for the switch like any other; its verdict goes into the model as `core.self`, so it counts in the summary and in the strict shield. A file that differs, is missing or is extra, a process not as it should be, or a manifest that is not good (another key, unreadable, older than one seen, dated in the future, expired) is a warning; no manifest (`missing`: a build by others than gAudit's release, such as a distribution's package) or no key is *unknown*; in a developer build, which runs from its build tree and has nothing to compare with, the same with nothing else found is *does not apply* (the information icon; the row says what was checked, "The program runs as it should; its files are not checked in a developer build", since "not checked" beside "checked at" reads as a contradiction, John 2026-11-17), not counted in the model or the strict shield, so the summary is not made unknown by it; never outside developer builds (`gaudit_self_not_applicable`). The row leads to *The Program's Self-Check* (`src/gui/gaudit-self.c`): what was checked, the signed list's state, the files and the processes by name, and what it means in plain words: a difference is not proof of an attack (a file changed by hand gives the same), but gAudit's results cannot be relied on while it is so, and the way to be sure is a check from a USB stick the computer is started from and installing gAudit again; an OK says no signs were found, not that the computer is clean.
- **The root-owned log (implemented, 2026-11-16).** The helper appends one line per command to `/var/log/gaudit/helper.log` (time, caller, command, checks that succeeded and failed; readable by all, nothing private), so what the user's side keeps can be compared with it afterwards.

## Integrity of the app itself

- A binary cannot verify itself. Checks are done by another component, and the helper is the anchor.
- The helper:
  - verifies GUI, orchestrator and rule engine against the manifest
  - inspects `/proc/<pid>/exe`, `/proc/<pid>/maps` and the environment of the orchestrator and rule engine
  - checks `/etc/ld.so.preload` and `.desktop` overrides
- The helper writes results to a root-owned log (`/var/log/gaudit/`), so a forged GUI can be exposed afterwards.
- Signs that the app has been modified must always raise a warning.

## Linking and dependencies

- **Everything links dynamically against Ubuntu packages.** Static linking was rejected as the general rule, because it would require us to track security updates in third-party code ourselves. We do not have capacity for that.
- The helper is kept minimal: glibc, libcap and libseccomp, plus libsodium once it verifies the manifest. It is not linked against the backend library.
- Trust levels:
  1. **Our own code:** verified with the signed manifest.
  2. **Ubuntu packages:** verified with `dpkg --verify`. This catches user-level changes and clumsy root changes, but dpkg's md5sums are not signed after installation. A deeper check following apt's signed chain (`InRelease` → `Packages` → `.deb`) is optional and comes later.
  3. **Running processes:** `maps` is checked against an expected library list, derived from the packages rather than maintained by hand.

## Acting on the system (deliberate exceptions)

gAudit mostly reads. It changes the system only in these deliberate ways, always on the user's request, through the helper and with the administrator password. No configuration of any kind is written without a deliberate, informed choice by the user: what is written where is shown first, and nothing happens until it is confirmed (John, 2026-11-19).

**Profiles are the general pattern.** gAudit may set something up only if there is a profile that automates the whole job: the user picks one of a few predefined profiles, and gAudit applies it. No per-item tailoring; when a setup needs tailoring, the simple approach no longer works and the user needs knowledge gAudit cannot assume. Examples: ClamAV scan schedules, automatic updates (security only / all / notify only), the firewall.

- **Where a fix ends (working rule, to be settled case by case).** A fix is within gAudit if it can be specified as a sequence of unambiguous steps the user clicks through, each of them safe on its own. If it needs data from the user that gAudit cannot find out itself, it belongs in specialised software. The line is fuzzy and is drawn when a concrete case comes up.
- **Usage questions combine profiles.** Instead of one profile for everything, the user answers a few yes/no questions about how the machine is used ("I play games", "I run web servers", …). Each answer maps to fixed profile parts, and the parts are combined (mix and match). Proposed rules (to confirm):
  - only yes/no answers, each with fixed rules, so the result stays automatable;
  - parts are combined as a union; where they disagree about a port, closed wins unless a "yes" answer explicitly needs it open;
  - answers are also checked against the machine: "no web servers" while something listens on port 80 is a finding, not something to close silently;
  - the answers may live in the user's settings, but applying them always goes through the helper, shows the plain-language summary of the changes first and needs the administrator password, so a changed answer cannot open a port unnoticed.
- **Rules decide, the helper writes.** A profile's Guile rules return a structured decision, never file text, e.g. `(profile (open (port 22 tcp lan)) …)`, using only values from the owning plugin's fixed vocabulary. The helper (C) checks the decision against that table and renders the file from a fixed template to a fixed, gAudit-owned place (e.g. a drop-in). A bad rule can at worst choose a poor combination of allowed values; it can never inject syntax or pick a target. The protection is the vocabulary, the templates and the signature or local approval, not the user reviewing the result: an ordinary user cannot judge whether a configuration file is right. What the user sees, and confirms, is a plain-language summary ("Opens SSH (port 22) to the local network"), built from fixed message ids for the same decision the helper renders, never from text a rule or plugin supplies, so the summary cannot claim one thing while the file does another. The rendered file carries the same summary as a comment (English, since the helper never translates). The summary is transparency, not protection. New knowledge about environments (which ports when, how answers combine) changes in Guile without recompiling; a new file format needs new C code, since the formats are the attack surface.
- **Firewall profiles** may depend on what is installed, e.g. open the ports a known program needs when that program is present. Safeguards: the program is detected through the package database, never by a file in the user's area or on `PATH` (user-level malware could plant one to get a port opened); the ports come from the profile's fixed table, never from the program; the plain-language summary is shown before it is applied; and ports are opened for the local network only unless the profile says otherwise.

- **Editing is started by the user, done automatically, and stopped when in doubt (John, 2026-11-15).** gAudit never starts a change on its own; *Run* starts it, and the change itself is automatic. Before writing, the helper checks preconditions on every file involved, each one *absent*, *has digest X* or *gAudit's own with digest Y* (from a root-owned register of what gAudit wrote: path, digest, template and values, as `ucf` keeps for Debian). The register and the writing are gAudit's own, in the helper's C, modelled on ucf but not using it (John, 2026-11-15): ucf exists only in the Debian family, so the other distributions would need a second way of writing as root, and there must be one code path to keep secure; ucf is also a shell script driven through debconf, which the minimal helper should not start as root. Removing the package removes what the register lists (`postrm`). If one fails, nothing is written and the problem is described instead, with what would have been written. Afterwards the effective value is checked again with the plugin's own collection, never assumed; if another file overrides it, the report names that file and gAudit leaves it alone. For *Updates* almost everything is done as drop-ins under gAudit's own names (e.g. in `/etc/apt/apt.conf.d/`) with the register; a package's conffile is not edited, since dpkg then asks at the next upgrade. Whether gAudit may ever replace a foreign file whose content is identical to a known version is still open.

The deliberate ways so far:

- **Fixing the user's own files' permissions (John, 2026-11-15; implemented for Private Files).** A fix page's command field has a button beside the copy button that runs the fix. It first makes the same check as copying (the field must still show the command it was made from); what runs is never that text, but a fixed operation of the plugin (`gaudit-orchestrator fix make-private <root> <path>`, `fix close-home <home>`), its arguments from the cached collection. The orchestrator does it as the user, without a password: it opens the file beneath its root without following any symbolic link (`openat2` with `RESOLVE_BENEATH | RESOLVE_NO_SYMLINKS`), checks it is the user's, and changes it through that open file. The operations only ever take access away (others' bits; for the home folder others' write), so a fix can never open anything up, whoever asks for it. The page then says what the permissions are now. No shell, no chmod program. After a fix the finding is checked again (`gaudit-orchestrator secrets item <area> <root> <path>`, the same rules as the collection, the known locations first for the home folder; `(secret ...)` or `(secret-gone)`), never guessed from what the fix should have done: its line in the cache is replaced or removed, the summary's counts follow, a `(rechecked (count N) (when "HH:MM"))` line says so, and the cache tells its watchers (`gaudit_cache_watch`), so Home's row and an open report page are made again from it; the report notes that some findings were checked again after the search. Only the collection the fix page was made from is patched; a newer one has seen the file already (John, 2026-11-15). The button is safer than the manual way (no clipboard another program could change, no shell to read the text): a fix that has a fixed operation gets the button; the command field stays as its explanation and for those who want to do it themselves (John, 2026-11-15).

- **Automatic updates as gAudit's own drop-in (John, 2026-11-15; implemented for Debian and Ubuntu).** The *Install Updates Automatically* fix page (from the recommendation when automatic installation is off) offers *Switch On* only when the package database shows no admin tool that sets updates up (`software-properties-gtk`, `software-properties-qt`, `update-manager`, `synaptic`, `gnome-software`, `plasma-discover`, `app-center`): with one, a file of gAudit's would override what the tool shows and sets, so the page names the tool and leaves the setting to it, until that tool's sub-plugin takes over. *Switch On* writes `/etc/apt/apt.conf.d/52gaudit-automatic-updates` through the helper (`run automatic-updates-on`, conf-write.h decides whether it may, unattended-upgrades must be installed); *Remove the Program's Setting* takes it away again, only while it is as gAudit wrote it (`run automatic-updates-remove`). Each is confirmed first with a plain-language summary of what is written where; the run waits for the switch like any other; the helper's `(conf (template ...) (action ...) (result ...))` comes back as an event, and the page says what happened in gAudit's own words (written, unchanged, someone else's file, edited since, missing precondition, unsafe folder). After a change, the Updates collection runs again, never a guess. When gAudit's file is there (`own-setting`), the row "Updates are installed automatically" says "Set up by the program" and leads to the page, so it can be removed. Every configuration gAudit writes uses `gaudit_fix_page_new_conf`, the standard for such pages (John, 2026-11-15): two buttons at the end, side by side and both always in view: *Undo*, then the apply button with its own short label (*Switch On*) and the accent, as the default. Never one button that turns into the other: undoing must take moving the pointer, so a second click cannot undo what was just done, and *Undo* being there is the promise that the action can be undone. Each is greyed out while it has nothing to do: *Switch On* once the setting is in place, *Undo* until then and again once it has been undone. A greyed default button loses its accent, so it looks like any inactive button, not a faded default (John, 2026-11-16; one CSS rule for the whole app, `button.suggested-action:disabled`). On a page that is like a dialog and follows a progression (such as a known vendor package's page; not a page whose action can be undone, which has the two buttons above), the buttons sit at the end, the last one shown is always the default, and a button whose step is over stays grey whatever came of it (a check that found nothing newer, or could not find out, too); only opening the page again starts a new sequence with active buttons, the last result shown (John, 2026-11-16). Such a page is built step by step into one process (John, 2026-11-17): each step is a text presenting what is to be done, with its button or buttons under it, and nothing under the button until it is pressed; the result then comes under the button, and if there is a next step, a new text with its own buttons comes under that (on *Update Zoom Yourself*: the version found, then *Install*; its outcome, then the weaker signature and *Install Anyway*). This is for such sequence dialogs only, not for fix pages with command fields. Such a page grows only downwards: what appears as the sequence goes (results, new buttons) comes after everything else, and nothing that is already shown is pushed down by it. GTK left the old pixels of a dimmed note that moved down (the top of its second line, under the version line on *Update Zoom Yourself*), with both its renderers, until the window was drawn anew. So on every fix page (`gaudit_fix_page_new`) the note comes right after what to do, before any command field, step or button, and what a page adds of its own goes after it; a command field's result line is there from the start, empty, so a short result moves nothing below it (a result of several lines still does, on pages with several steps; to be polished if it shows) (John, 2026-11-17). A run button beside a command field's copy button also stays grey once its run is over, whatever came of it, since such a command is usually meant to be done once and running it twice may cause a problem (almost cosmetic for `apt-get update`, real for others) (John, 2026-11-16). On a fix page whose rows each have a run button, buttons that do the very same operation (the same arguments, not just the same words) know each other, and once one is pressed the others go grey with it, so the same operation is never run twice from one page into conflicting states (back again only if the run never started); when every row would do the very same, they are one row instead (John, 2026-11-16; `gaudit_fix_page_new_steps`). *Undo* is plain, never the default and without the accent, with what it undoes as its tooltip ("Remove the Program's Setting"), since people avoid long labels; the confirmation's heading says it in full (John, 2026-11-15).
- **Running a system tool from a fix page (John, 2026-11-15).** The user acts: pressing *Run* is a deliberate choice, and gAudit's part is to make sure what happens is what the page shows. So the command field shows exactly the command that runs, options and all (`-y` included), and that is what is copied too; below it, the page says in plain words what each part does (e.g. that `-y` answers yes on the user's behalf, that changed settings files are kept), so the user gives informed consent whether pressing or copying. The shown text and the helper's argv come from one shared table, so they cannot drift apart (a test holds them equal); the run button sends only the operation's name, never the text. Only gAudit's own operations have an undo (its drop-in, which it wrote and can take away again; the page's *Undo* can be used once it is written): what a system tool changes, through its packages' scripts and new dependencies, cannot be known in full, so a command run on the command line has none, and its explanation says so (John, 2026-11-15). Commands gAudit cannot keep in hand are not offered to run: no compound commands, pipes or anything through a shell; a multi-step fix is shown as steps, each with its own field and buttons, even if it takes more clicks. Where gAudit can do a thing directly (its own drop-in for automatic updates), that is safer than a cryptic command, and a plain button is fine. Package managers run their packages' scripts, so these run as root without the helper's sandbox; apt refuses unsigned packages unless told otherwise, and gAudit never tells it otherwise. `apt upgrade` never fetches the package lists itself (checked in Debian 12 and 13, Ubuntu 24.04 and 26.04); `--update` does, from apt 2.7.0 (its changelog), so with apt 2.7.0 or newer the upgrade is one command, otherwise two steps.
- installing missing packages (PackageKit, see *User interface*);
- **ClamAV: selectable profiles.** The user picks one of a few predefined profiles, and gAudit sets it up (e.g. a scheduled scan as a systemd timer, plus the matching update schedule). A profile must be fully automatable: no per-item tailoring, because once a setup needs tailoring, the simple approach stops working and the user needs knowledge gAudit cannot assume. A profile's scan can also be run on request; the result is a report, and the run is a background job with progress. Units gAudit creates are named as gAudit's, can be removed again from the app, and are logged; existing configuration made by the user or another tool is never edited. Anything more specialised is left to ClamAV front ends.

## Built-in tasks

- **Firewall (`core.firewall`, implemented):** the first task with page 1 and page 2, written in C until the plugin description format exists (it then moves there, marked `core`). The helper reads the nftables ruleset over netlink itself (`src/plugins/firewall/helper/nft.c`, no libnftnl, so the helper stays minimal) in a child that stays root with exactly `CAP_NET_ADMIN` (the kernel refuses even reading the ruleset without it), and counts loaded legacy iptables tables from `/proc/net/ip{,6}_tables_names`, which nftables does not show. It reads, never changes.
  - Interim verdict, in C until the rule engine takes over (`gaudit_firewall_verdict`): *OK* when incoming traffic meets a filter chain on the input hook (ip, ip6 or inet) that drops by default (ufw) or has rules (firewalld); *warning* when there is none or it accepts everything; *unknown* when there is no nftables input filter but legacy iptables tables are loaded, since their rules are out of sight.
  - An OK result says the firewall is active, not that its rules suit the user.
  - A warning shows what the missing firewall leaves open (the orchestrator counts the listening services when the check runs) and the manual way to switch it on: a copyable command from a fixed table (`sudo ufw enable`, `sudo systemctl enable --now firewalld`), chosen by which program the backend sees installed, with a note to allow remote access such as SSH first. gAudit never runs it; the user does. A graphical firewall manager is not suggested: that is not a security finding.
  - Not yet: storing the report, history, the run as a background job with toasts, recording the result on Home.

- **Private Files (`core.private-files`, implemented, `src/plugins/private-files/`):** the deep scan of the home directory as a plugin, the first one above *Quick* that needs no password. Its full collection is the known-locations check first, exactly the code Home counts with (`gaudit_private_files_each`), then the deep scan, each path reported once; `tests/test_secrets_collect.c` holds that everything Home finds is in the full list. It runs as the user in an orchestrator of its own (`gaudit-orchestrator secrets`; the GUI's run command is `user secrets`), never through the helper. At most 100 findings are sent, those others can reach first, then a summary that counts them all, parsed strictly (`common/secrets.h`); paths are relative to home and never leave it. Verdict: a warning when anyone but the user can reach a secret (other groups or every account; the user's own private group counts as the user), unknown when the search failed or stopped at its limit with nothing reachable found, otherwise OK, since secrets only the user can read are normal. Its report is the rule script `rules/report.scm` (the verdict is decided there and nowhere else): page 2 lists the findings by reach, and each one others can reach leads to its own fix page with `chmod go-rwx -- ~/'…'` (`chmod go-w ~` for the home folder). The plugin builds that page from the cached collection line (`gaudit-private-files.c`), never from the report, and gives a command only for files the user owns whose names were sent exactly (a replaced byte would point the command at another file). Nothing is stored on disk; the collection lives in memory for the session. Its parameters (implemented, John, 2026-11-14): folders to include, modelled on Pika Backup's list of folders to back up, but include only, no exclusions. The home folder (from the password database) is always the root; the user may add more folders, elsewhere on the machine or on a network, and the whole tree under each is searched, within that folder's own filesystem. Reach is judged from `/` down to each file for an added folder (the folders above it only looked at with `stat`, never listed); the home folder is read only from itself down. Findings on network filesystems are marked uncertain (modes and owners there may not say who can reach a file on the server). The folders are kept in GSettings (relocatable schema `<app id>.plugin`, key `folders`, at `/…/plugins/<plugin id, dots as dashes>/full/`), read back checked (`gaudit_task_folders`: absolute, printable, no `..`, below 256 bytes, at most 15), passed to `gaudit-orchestrator secrets full <folder>...` one argument each, canonicalised there; a folder that overlaps the home folder or another one is named but not searched, one that cannot be opened is named as such. Every report lists the areas it searched. The file manager's places come along (John, 2026-11-14): GTK bookmarks (`~/.config/gtk-3.0/bookmarks`), KDE places (`user-places.xbel`), `/mnt/<user>` when it belongs to the user (an administrator's convention, not shown by file managers) and mounted disks and network folders (GIO's volume monitor), one by one; `/media/<user>` and `/run/media/<user>` themselves are only mount points, so not listed as such. Those under the home folder are left out (searched with it); those elsewhere are on the list with the home folder, marked *From the file manager*, and can be removed. A removed place is remembered (`removed-places`) and comes back only if the user adds it again; that is a stored exclusion, but never shown as an exclusion list, because a list of what is searched is easier to understand. The places come from the user's own area, so the worst a planted one can do is add a folder to search; the report names every folder searched. Places that do not exist (a disk not plugged in) are left out. *Parameters* shows the home folder (always searched, cannot be removed), the added folders and places with a button to remove each, and *Add a Folder to Search* (a folder chooser); next to *Start* a note says the parameters apply to the full report only, not to Home. A fix's command is built from the finding's area (`fix_page` gets the cached lines, so it can find the area), and on a network folder the fix page says the server decides. Parameters are for the full run only: Home never uses them (tentative), so Home stays the same condensate every time and page 2 a superset of it. On Home it reports at every level, each from its own collection with the rule script (John, 2026-11-14: *Quick* is a report too): *Quick* collects the known locations only (`user secrets quick`), *Thorough* also searches the whole home (`user secrets full`, also the full run on page 2); the rule gets the level and says on *Quick* that only the usual places were checked. Home shows a condensate of what fails (see *Home condenses what fails*), never all of page 2's rows. A task gives its collection command per level (`home_commands`); `gaudit_task_home_command` picks the nearest at or below the chosen level, which is the fallback. The group's chevron is always there.

## Example checks

- Updates: when they last ran, whether automatic updates are on, and whether security updates are pending.
- Firewall: ufw/nftables (firewalld later), and whether it is actually active.
- Antivirus: whether ClamAV is installed, whether `freshclam` updates, and whether a scheduled scan exists (systemd timer or cron).
- Disk encryption (LUKS) and Secure Boot.
- Screen lock, automatic login, SSH server and services listening externally.
- Signs of tampering: `/etc/ld.so.preload`, unknown kernel modules, and whether the kernel is "tainted".

## i18n and l10n

- gettext with text domain `gaudit`. Source strings (msgid) are English; the first translation is `nb`.
- More translations are deferred. The maintainer can review nb, nn, da and sv; any other language needs a native reviewer before it ships.
- `po/` holds `POTFILES.in`, `LINGUAS` (one language code per line), `gaudit.pot` and `<lang>.po`.
- `.desktop` and polkit files are translated with `msgfmt --desktop`/`--xml`. Ubuntu ships no ITS rules for polkit, so our own are in `po/its/`, found via `GETTEXTDATADIRS`.
- **Only the presentation layer translates.** The protocol between processes and the helper's output are language-neutral, with stable keys such as `firewall.active`. The helper never translates: it runs as root, and locale from the user environment is not trustworthy there.
- Guile rules return message IDs and parameters; the GUI translates. Translatable strings in rule files are extracted with xgettext (Scheme).
- **Translations are part of integrity.** A modified `.mo` file can make a red finding read as green. Therefore:
  - The locale directory is compiled in; no environment variable can override it.
  - `.mo` files are verified like other package files.
  - Translations downloaded together with rules must be listed in the signed manifest.
- New or changed text: `cmake --build --preset default --target update-po`, then translate in `po/*.po`.

## Layout

```text
src/gui/           GUI in C (controller: gaudit-app, view: gaudit-window, task pages)
src/model/         model in C++ behind a C API (include/gaudit/model.h)
src/backend/       distro interfaces (include/gaudit/backend.h), os-release, collector runner, debian/, fedora/, arch/, generic/
src/probe/         unprivileged status probes for Home (include/gaudit/probe.h), no GTK
src/collectors/    separate collector programs (flatpak/: libflatpak, snap/: json-glib, dnf/: libdnf5 (C++), pacman/: libalpm)
src/helper/        privileged helper (pkexec)
src/plugins/       built-in plugins, one folder each (firewall/, updates/, private-files/)
src/orchestrator/  orchestrator (user)
src/engine/        rule engine (Guile)
data/              .desktop and polkit policy (templates with @VAR@); icons/ (compiled into the GUI as a GResource, data/gaudit.gresource.xml)
po/                translations; its/ holds ITS rules for polkit
cmake/I18n.cmake   gettext targets: pot, update-po, translations
tests/             hand-written tests
```

- **Each built-in plugin has its own folder** under `src/plugins/` (decided 2026-11-14). Its code is grouped by the process it runs in, and the folder's `CMakeLists.txt` adds the sources to that process's target, so nothing of a plugin runs anywhere else: `plugin.c` and other top-level files go into the GUI (the description, `gaudit_plugin_<name>`, listed in `src/gui/gaudit-plugins.h` and `gaudit-task.c`, and its presentation), `helper/` into the privileged helper, `backend/` into the unprivileged probes and collectors. Shared code (protocol, runner, generic pages) stays where it is. This keeps plugins apart until the description format and the rule engine exist, so moving to them goes one folder at a time. Not moved yet: the plugins' parts of `gaudit/run.h`, `run-io.c` and `gaudit-run-page.c`, and the Home groups table in `gaudit-window.c`.
- Helper, orchestrator and engine are installed in `libexec/gaudit/`. `Exec` in the desktop file and `exec.path` in the polkit policy are absolute paths.
- Dependencies to install when first used: `guile-3.0-dev`, `libsodium-dev`, `libcap-dev`. `libseccomp-dev`, GTK4 and libadwaita are already present. `libflatpak-dev` is optional at build time; at run time the collector needs `libflatpak0`.

## The wiki

- **The user documentation is the GitHub wiki (John, 2026-11-16).** It lives in its own repository, `github.com/jeblad/gaudit.wiki.git`, checked out as the submodule `wiki/` (fetched over https so anyone can clone it; John pushes over SSH by a local push URL). Users may edit it directly, so it is where the text lives: what is written in `wiki/` is a draft until pushed, and changes made on GitHub are pulled back with `git -C wiki pull`.
- **What it is for (John, 2026-11-16):** a summary of what gAudit does, why it does things the way it does, and the effect that is wanted. Every rule a user may meet is explained in plain text, never left in comments, with concrete cases by name (Zoom, Discord, CUDA, libx11), so a result that looks like a mistake can be answered with a link instead of an issue. Written in English, for two kinds of reader (John, 2026-11-16): users who need a small push to understand how things work, and amateur or family admins (the one who looks after the family's computers, often a teenager, John 2026-11-16) who do not quite have the hang of how such things are done. The tone takes them seriously and gives them a bit of credit: looking after others' computers is real work, the pages explain the why so what they learn carries beyond gAudit, and nothing talks down to them. The language is plain on purpose, so most people can follow it, and Home says so: to professionals it may read as simplified, which is a choice, not a mistake. Plain is never vague: each term means one thing throughout, and a word with a precise meaning in the field is used with that meaning (John, 2026-11-16). So each page explains a term where it is used, in a sentence (software source, signature and key, PPA, administrator rights), says how the thing is usually done and why (the good practice behind the rule), and what the reader can do next, also where gAudit itself does nothing. Not for developers: AGENTS.md is not a source to copy from.
- **Its layout:** `Home`, `Principles`, one page per plugin, and sub-pages where a plugin has many rules (`Updates-…`); file names use hyphens, never colons, so the wiki clones everywhere; `_Sidebar.md` holds the navigation. A page says which gAudit version it describes.

## Versioning and releases

- The version lives in `VERSION` (one line, e.g. `0.1.0`). `CMakeLists.txt` reads it into `project()`, so it reaches `config.h`, the About dialog and the `.pot` header.
- Releases use **commit-and-tag-version** (configured in `.versionrc.json`). It bumps `VERSION`, updates `CHANGELOG.md`, commits and tags `vX.Y.Z`. The maintainer runs it, because it writes git history.
- Commit messages follow **Conventional Commits** (`feat:`, `fix:`, `docs:`, `chore:` …; `!` or `BREAKING CHANGE:` for breaking changes), since the changelog and the version bump are derived from them. Below 1.0.0, breaking changes bump the minor version.
- The project stays on 0.x until it is reasonably functional. 1.0.0 is a deliberate step (`--release-as 1.0.0`); the tool never reaches it by itself.
- Run the tool with a pinned version (`npx commit-and-tag-version@<exact version>`), never an unpinned `npx` download.

## Build and test

- CMake with presets:
  - `CMakePresets.json` (tracked) defines `dev` and `release`.
  - `CMakeUserPresets.json` (local, git-ignored) defines `default`, inheriting `dev`.
- Commands:
  - configure: `cmake --preset default`
  - build: `cmake --build --preset default`
  - test: `ctest --preset default`
- Parallelism is capped at 6 build jobs and 4 test jobs, because the machine has only 16 GB RAM. Never use unbounded `-j` or `--parallel`.
- `GAUDIT_DEVELOPER_BUILD=ON` (in `dev`) reads translations, collectors, the orchestrator and the GSettings schema from the build tree, through compiled-in paths (never `GSETTINGS_SCHEMA_DIR` or other environment variables). Never use it for packaging.
- **Every icon the app uses is bundled**, so none is ever missing (no red "missing icon" blobs, whatever theme or icon packages the user has). They live in `data/icons/scalable/actions/` and are compiled into the GUI as a GResource under `/io/github/jeblad/gaudit/icons`, which `GtkApplication` adds to the icon search, so they are found by name. The active theme still wins where it has the same name, so the look follows the user's theme; the bundled ones are the fallback. Source and license go in a comment in `data/gaudit.gresource.xml` and in the README's acknowledgements: from adwaita-icon-theme under LGPL-3.0 (dual LGPL-3.0/CC-BY-SA-3.0), from the GNOME icon library (CC0, exported with the *Icon Library* app), or from Yaru (icons CC-BY-SA-4.0, © Sam Hewitt; one-way compatible with GPL-3.0; check the copy is identical with the theme's file, since the Icon Library app also serves icons already on the machine). A new icon in the code needs its SVG added there too. **Own names where the meaning matters:** an icon whose interpretation is important, used for what it normally means, gets a `gaudit-` name so no theme can replace it; everything else follows the theme. Home's summary shield is the first case: Yaru draws every security level as the same shield in another colour, which says nothing to a colour-blind user. The shields are `gaudit-status-ok` (check mark: every check passed, including those that need the password, from this session), `-high` (the checks without the password passed), `-medium` (warning), `-low` (serious) and `-unknown` (question mark), all on the Adwaita shield outline, so the shape carries the level. A single unknown makes the summary unknown (`gaudit_model_summary`), since the outcome is then not known. When the shield changes after the status is in, it fades into the new one (`gaudit-crossfade.c`; skipped when animations are off). The user/administrator switch is `gaudit-user-symbolic` (one person) and `gaudit-superuser-symbolic` (two, the front one in the accent colour) for the same reason. The sidebar icons have own names too (`gaudit-home-symbolic`, `gaudit-fire-symbolic` for the firewall), so each page stays recognisable whatever the theme. A recommendation in a report (advice) shows `gaudit-information-symbolic`, Adwaita's information icon under gAudit's own name (John, 2026-11-15). A Home row that cannot run until the user switches to administrator shows `gaudit-questionmark-symbolic` instead of the plugin's own icon, since something must be done (John, 2026-11-15). `gaudit-fire-symbolic` and `gaudit-questionmark-symbolic` use GTK's newer stroke-based symbolic format: right with GTK 4.24; older GTK may not recolour strokes, so a filled variant may be needed for older distributions.
- GSettings schema `io.github.jeblad.gaudit` (`data/gaudit.gschema.xml.in`) holds the window size and state. The window opens the schema through `g_settings_schema_source_lookup` first, so a missing schema means "remember nothing", never the abort `g_settings_new` would cause. The relocatable schema for plugin parameters will go in the same file.
- **Pretending software is missing (developer builds only):** `gaudit --pretend-missing=ufw,clamav` makes the GUI and the status orchestrator treat those capability ids as not installed, to see the pages for missing software without uninstalling anything. It is a command-line switch, never an environment variable, and is compiled out of other builds (`GAUDIT_DEVELOPER_BUILD` in `config.h`), so a packaged gAudit cannot be talked into hiding a tool. Only `[a-z0-9-]` and commas are accepted. The helper does not take it: the firewall check itself still reads the real ruleset.
- Hardening is on for all targets: stack protector, stack clash protection, CET, `_FORTIFY_SOURCE=3` (not in Debug), PIE and full RELRO with `BIND_NOW`.
- Targeted, hand-written tests over clear execution paths, not a heavyweight test framework.
- **Other distributions are tested in two layers:**
  - In every normal session, backends for other distributions are tested against small fixtures in `tests/data/` (e.g. an rpm database and dnf metadata taken once from a container). They need no container and run with `ctest`.
  - Real runs happen on demand with `tools/distro-test.sh fedora|arch|opensuse|debian`, never as part of `ctest`. It uses rootless podman (no root daemon; docker is not used), mounts the source read-only, builds and tests inside a `--rm` container, runs `gaudit-probe-dump`, and removes the image afterwards, so nothing stays on disk. Disk space is needed for other things.

## Open questions

- What happens to a plugin's reports when the plugin is deleted. Deferred.

- Granularity of plugin trust. Today the signed list approves *owners*, and revocation works per owner. For owners we do not know, should approval also cover the specific plugin and version? Still under consideration.
- Hard revocation versus semi-blocking. With semi-blocking, an owner removed from the trust list becomes "unknown", and the user could approve their plugins locally. Should there also be an explicit block list in the signed file, which local approval cannot override?
